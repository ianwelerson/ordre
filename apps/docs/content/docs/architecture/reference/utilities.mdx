Small, dependency-light helpers that live in `apps/api/src/utils`. They are
framework-agnostic (no Express) so controllers can call them directly, and each
one is unit-testable in isolation. This page is the index - reach for a helper
here before writing another one.

A helper a frontend also needs lives in `@ordre/core/utils` instead, so both
sides of the wire run the same code. `slugify` is there, and it is documented
under [`@ordre/core`](/internal-docs/architecture/packages#utilities). The ones
below stay in the API, either because they touch the database or because their
data should not reach a browser.

| Utility                                   | Purpose                                                      |
| ----------------------------------------- | ------------------------------------------------------------ |
| [`audience`](#audience)                   | Resolve the Resend audience segments a member belongs to     |
| [`db-error`](#db-error)                   | Classify raw Postgres driver errors (unique violation, etc.) |
| [`outbox`](#outbox)                       | Queue a transactional message in the caller's transaction    |
| [`outbox-payload`](#outbox-payload)       | Re-parse a queued payload against its delivery's schema      |
| [`slug-restrictions`](#slug-restrictions) | Block reserved, brand-protected, and profane workspace slugs |
| [`testing`](#testing)                     | Assert a response body against a shared schema in a test     |
| [`validation`](#validation)               | Parse request bodies and normalize validation errors         |

## `audience`

`apps/api/src/utils/audience.ts`

Works out which Resend audience segments a person belongs to, so the `audience`
channel can reconcile their contact after a membership change. See
**[Transactional Outbox](/internal-docs/architecture/outbox)** for how the channel
consumes this.

**Exports:**

| Export                                          | Kind     | Description                                                                       |
| ----------------------------------------------- | -------- | --------------------------------------------------------------------------------- |
| `audienceSegmentsForSelf(transaction, userId)`  | function | The caller's own segments, read from their active memberships                     |
| `audienceStateForMember(transaction, memberId)` | function | Contact details and segments for another member, or `null` when they are not visible |

`audienceSegmentsForSelf` always includes `all-accounts`, because a contact only
exists here when an account does and Resend requires a segment to broadcast to.
It reads the caller's own rows, which the `member_select` policy allows across
every workspace.

`audienceStateForMember` goes through the `app_member_audience_state` database
function instead of a query, because RLS hides the target's other workspaces from
the caller. Pass the transaction that wrote the membership change, not the request
handle, or the segments reflect pre-change state.

## `db-error`

`apps/api/src/utils/db-error.ts`

Turns a raw database driver error into something a controller can map onto the
shared error catalog (`@ordre/core/errors`). Postgres reports failures with a
stable `SQLSTATE` code (e.g. `23505` for a unique violation); node-postgres
surfaces that as `error.code` alongside `error.constraint` / `error.detail`.
Drizzle sometimes wraps the driver error, so the helpers look at both the error
itself and its `.cause`.

This module only **classifies** the raw error - the controller stays in charge of
the domain mapping (which constraint means which business error).

**Exports:**

| Export                                  | Kind      | Description                                                                                          |
| --------------------------------------- | --------- | ---------------------------------------------------------------------------------------------------- |
| `PG_ERROR_CODES`                        | const     | SQLSTATE codes: `UNIQUE_VIOLATION`, `FOREIGN_KEY_VIOLATION`, `NOT_NULL_VIOLATION`, `CHECK_VIOLATION` |
| `PgErrorCode`                           | type      | Union of the values in `PG_ERROR_CODES`                                                              |
| `PgError`                               | interface | Narrowed driver error shape: `code`, `constraint?`, `detail?`, `table?`                              |
| `getPgError(error)`                     | function  | Unwraps a caught error into a `PgError`, or `null` if it isn't one                                   |
| `isUniqueViolation(error, constraint?)` | function  | `true` when the error is a unique-constraint violation; pass `constraint` to match a specific index  |

**Usage** - the unique index is the real guard against a duplicate slug, so a
concurrent insert that slips past the pre-check is caught here:

```ts
import { isUniqueViolation } from '#/utils/db-error.ts';

try {
  await db.insert(schema.workspace).values(data);
} catch (error) {
  if (isUniqueViolation(error)) {
    return errorResponse(WORKSPACE_ERRORS, 'WORKSPACE_SLUG_ALREADY_EXISTS');
  }
  throw error;
}
```

Once a table has more than one unique index, pass the constraint name to
disambiguate which one collided:

```ts
if (isUniqueViolation(error, 'workspace_slug_unique')) { ... }
```

## `outbox`

`apps/api/src/utils/outbox.ts`

The producer side of the transactional outbox: queues one delivery in the caller's
transaction and wakes the delivery worker once that transaction commits. The full
design - worker, retries, dead-lettering, adding a topic - is on its own page:
**[Transactional Outbox](/internal-docs/architecture/outbox)**.

**Exports:**

| Export                             | Kind     | Description                                                              |
| ---------------------------------- | -------- | ------------------------------------------------------------------------ |
| `pushToOutbox(transaction, input)` | function | Inserts an outbox row and registers the worker wake-up via `afterCommit` |

`input` is `{ channel, topic, to, variables }`. `variables` is type-checked against
`<channel>:<topic>` minus the defaults `pushToOutbox` fills in, so a missing or
misspelled variable is a compile error at the call site.

```ts
import { pushToOutbox } from '#/utils/outbox.ts';

await pushToOutbox(tx, {
  channel: 'email',
  topic: 'workspace:created',
  to: user.email,
  variables: {
    workspace_name: data.name,
    workspace_industry: data.industry,
    workspace_plan: freePlan.title,
    owner_email: user.email,
  },
});
```

> Pass the transaction **explicitly**. Inside a nested `getDb().transaction(...)`
> the insert belongs to that `tx`, or the row survives a rollback of the block that
> produced it. Everywhere else `getDb()` is already the request transaction.

## `outbox-payload`

`apps/api/src/utils/outbox-payload.ts`

The consumer side of the same contract `pushToOutbox` writes. The worker re-parses
each claimed row against the schema for its `<channel>:<topic>` delivery, so a
payload queued before a schema changed fails loudly instead of rendering a
half-empty template.

**Exports:**

| Export                                    | Kind     | Description                                                             |
| ----------------------------------------- | -------- | ----------------------------------------------------------------------- |
| `parseOutboxPayload(delivery, payload, id)` | function | Returns the typed payload, or throws naming the row and the bad field |

The thrown message carries the row id and a flattened list of field errors,
because it lands in the row's `last_error` column and that column is the only
place the failure is debuggable afterwards.

## `slug-restrictions`

`apps/api/src/utils/slug-restrictions.ts`

Guards workspace slug creation against names that must never be granted. It runs
**before** the uniqueness check in `workspaceCreate`, and backs the
`WORKSPACE_SLUG_RESERVED` / `WORKSPACE_SLUG_PROTECTED` / `WORKSPACE_SLUG_BANNED` errors in
[Error Codes](/internal-docs/architecture/reference/error-codes).

Checks run in priority order:

| Restriction                | What it covers                                                                                                     |
| -------------------------- | ------------------------------------------------------------------------------------------------------------------ |
| `WORKSPACE_SLUG_RESERVED`  | Platform / system names needed for routes, subdomains, and auth (`api`, `admin`, `settings`, ...). Never grantable. |
| `WORKSPACE_SLUG_PROTECTED` | Well-known brands / trademarks (`apple`, `nike`, `stripe`, ...). Grantable only to a verified owner.                |
| `WORKSPACE_SLUG_BANNED`    | Profanity and slurs, matched after normalization.                                                                   |

**Profanity matching** is deliberately careful about false positives:

- Input is **normalized** first - lowercased, de-leeted (`b1tch` -> `bitch`,
  `@ss` -> `ass`), and stripped of non-letters so separator evasions like
  `f-u-c-k` collapse into one token.
- Strong terms (`fuck`, `shit`, ...) match **anywhere** in the normalized slug.
- Short / embeddable terms (`sex`, `anal`, `coon`, ...) match only when they are
  the **whole slug or a full delimited segment** - so `my-sex-shop` is blocked
  but `sussex`, `analytics`, and `raccoon` are not.

**Exports:**

| Export                     | Kind     | Description                                                                            |
| -------------------------- | -------- | -------------------------------------------------------------------------------------- |
| `getSlugRestriction(slug)` | function | Returns the matched restriction as a `WorkspaceSlugRestriction`, or `null` when allowed |

The return type is `WorkspaceSlugRestriction` from `@ordre/core/enums`, whose
values are `WORKSPACE_ERRORS` keys checked with `satisfies`. A restriction is
therefore already the error code, so it goes straight to `errorResponse` with no
string building in between, and renaming a code in the catalog fails the build
here rather than producing an unknown code at runtime.

```ts
import { getSlugRestriction } from '#/utils/slug-restrictions.ts';

const restriction = getSlugRestriction(data.slug);

if (restriction) {
  return errorResponse(WORKSPACE_ERRORS, restriction);
}
```

The same values back the `reason` field on the slug availability endpoint, which
adds `WORKSPACE_SLUG_ALREADY_EXISTS` for the uniqueness case. Both lists live in
`WORKSPACE_SLUG_RESTRICTIONS` and `WORKSPACE_SLUG_UNAVAILABLE_REASONS`.

> Expects an already-normalized slug (lowercase, hyphenated) - the same shape
> `WorkspaceCreateSchema` produces via `.slugify()`.

## `testing`

`apps/api/src/utils/testing.ts`

Test-only helper. Validates a response body against a shared Zod schema and
returns it typed, so a test asserts the *shape* once and then only the *values*
that matter, instead of re-listing every field.

**Exports:**

| Export                     | Kind     | Description                                                       |
| -------------------------- | -------- | ------------------------------------------------------------------ |
| `parseBody(schema, body)`  | function | Returns the parsed body, or throws with the reason and the payload |

On a mismatch it throws with a prettified Zod error plus the received body, so a
failing test points straight at the offending field. See
**[Testing](/internal-docs/start/testing)** for where each tier uses it.

## `validation`

`apps/api/src/utils/validation.ts`

Bridges Zod and Better Auth validation into the API's standard
`ResponseErrorBody` shape, so every failure returns a consistent `INVALID_INPUT`
body with a per-field `details` map.

**Exports:**

| Export                                      | Kind     | Description                                                                              |
| ------------------------------------------- | -------- | ---------------------------------------------------------------------------------------- |
| `validateRequestBody(schema, payload)`      | function | Parses a payload against a Zod schema; returns parsed data or a ready-to-send error body |
| `parseBetterAuthValidationDetails(message)` | function | Splits Better Auth's flattened `[path] message` string into a `{ field: message }` map   |

### `validateRequestBody`

Wraps `schema.parse`. On success it returns the parsed (and transformed) data; on
a `ZodError` it returns an `INVALID_INPUT` error body whose `details` map each
field path to its message. Non-Zod errors are rethrown for the caller to handle.

```ts
import { validateRequestBody } from '#/utils/validation.ts';

const parsed = validateRequestBody<WorkspaceCreate>(WorkspaceCreateSchema, payload);

if (!parsed.success) {
  return { status: 400, body: parsed.error }; // { code: 'INVALID_INPUT', message, details }
}

const { data } = parsed; // fully typed + normalized
```

### `parseBetterAuthValidationDetails`

Better Auth concatenates every field error into a single string of
`[<path>] <message>` segments joined by `; `. This splits it back into a
`{ field: message }` object, stripping the leading `body.` prefix so keys match
the request payload:

```ts
parseBetterAuthValidationDetails('[body.email] Invalid input; [body.password] Too short');
// -> { email: 'Invalid input', password: 'Too short' }
```

Segments that don't match the `[path] message` shape are skipped, so a future
Better Auth format change degrades to a partial/empty object rather than throwing.
