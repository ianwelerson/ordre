## 🚀 Frontend Hosting - Vercel

**Status:** Chosen and active

**Why:**

- Purpose-built for Next.js (made by the same team); zero-config deployments
- Native App Router support and Turbopack optimizations
- Automatic preview deployments per PR; easy environment variable management
- Industry-standard choice for Next.js projects; strong portfolio signal
- Free Hobby tier covers development; Pro tier when monetised

**Plan:** Hobby (free) during development. Pro ($20/month flat, unlimited team members) once Ordre is commercial. The Pro plan's included bandwidth and serverless compute are more than sufficient for early production.

**Tradeoff accepted:** Some Vercel-specific features exist, but the core app is standard Next.js and remains portable.

## 🚂 Backend Compute - Railway

**Status:** Chosen

**Why:**

- Usage-based billing (per-second) - pay for actual CPU and RAM consumed, not reserved capacity
- Vertical auto-scaling: the container uses more resources under load and scales back down at idle, automatically
- Long-running process support - Express + Socket.io runs as a persistent server with WebSocket connections
- Git-connected deploys from GitHub with preview environments per PR
- Excellent CLI tooling for local development and deployment
- Hobby plan ($5/month, includes $5 usage credit) covers development and early production

**How it works:** Express runs as a containerised service on Railway. Under low traffic (e.g. overnight), the container idles at minimal CPU/RAM and the cost drops proportionally. During active hours, it scales up automatically - no configuration needed, no tier jumps. At the plan limits (8 vCPU, 8 GB RAM on Hobby), upgrading to Pro ($20/month per seat, includes $20 credit) raises the ceiling to 32 vCPU / 32 GB RAM and enables horizontal scaling via replicas.

**Environments:**

| Environment | Plan                        | Behaviour               |
| ----------- | --------------------------- | ----------------------- |
| Production  | Hobby ($5/month)            | Always-on, auto-scaling |
| Staging     | Free ($1/month after trial) | Scale-to-zero when idle |

**Alternatives considered:** Render (fixed tier pricing - $7 Starter with steep jumps to $25/$85; less cost-efficient at scale), Fly.io (removed free tier), Heroku (expensive for equivalent resources), self-managed VPS (operational overhead).

## 💾 Database - Neon

**Status:** Chosen

**Why:**

- Serverless PostgreSQL with true scale-to-zero - no idle instance cost during low-traffic periods or overnight
- Ordre's data is relational by nature - boards, workspaces, members, clients, updates, approvals
- Database branching for isolated dev/staging environments at no extra cost
- Drizzle ORM abstracts the driver - standard PostgreSQL throughout, fully portable via `pg_dump`/`pg_restore`
- Free tier (0.5 GB storage, 100 compute-hours per month) covers development and early production through ~100 owners

**Plan progression:** Free tier → Launch ($19/month, 10 GB, 300 CU-hours) → Scale ($69/month, 50 GB, 750 CU-hours) as usage grows.

**Data retention:** Active boards and archived boards are both stored with full history. Old boards remain accessible to clients via their original link.

**Alternatives considered:** AWS RDS PostgreSQL (always-on instance cost, AWS account required), Supabase (opinionated all-in-one stack), Aurora Serverless v2 (high minimum cost at low scale - 0.5 ACU floor).

## 📷 Image Storage - Cloudflare R2

**Status:** Chosen

**Why:**

- S3-compatible object storage with zero egress fees at any volume - images are served globally through Cloudflare's 330+ edge locations at no transfer cost
- Already using Cloudflare for DNS on `ordre.app` - R2 is in the same dashboard, same account
- Free tier (10 GB storage, 1 million writes, 10 million reads per month) covers development and early production with no expiration
- No separate CDN needed - Cloudflare's global network acts as the CDN automatically
- The AWS SDK and any S3-compatible library work with R2 via a config change (endpoint URL + credentials)

**Upload flow:** Workspace members upload photos via a pre-signed URL generated by the Express API. No file data passes through the API - the client uploads directly to R2.

**Image processing:** Thumbnails for timeline views are generated on upload to reduce transfer size. Full-resolution originals are served on click. Both are stored in R2.

**Alternatives considered:** AWS S3 + CloudFront (egress fees dominate at scale), Railway Object Storage (same storage price but charges egress with no CDN), Backblaze B2 (cheaper storage but requires Cloudflare CDN integration for free egress).

## 🔴 Cache & Real-Time - Upstash Redis

**Status:** Chosen

**Why:**

- Serverless Redis with pay-per-command pricing - no idle instance cost
- Used for WebSocket pub/sub (real-time board updates via Socket.io) and short-lived board data caching
- Free tier (500K commands per month, 256 MB) covers development and early production
- Low-latency global edge network
- Simple HTTP-based API alongside standard Redis protocol

**Tradeoff accepted:** Slightly higher latency than a self-managed Redis instance, but the operational simplicity and scale-to-zero pricing outweigh the difference for Ordre's use case.

## 🔐 Authentication -  Better Auth
**Status:** Chosen

**Why:**

- Open-source library that runs directly inside the Express app - no external service, no MAU pricing, no lock-in
- Session-based authentication with auth data stored in the Neon database alongside app tables
- Handles password hashing, session management, CSRF protection, and rate limiting out of the box
- Multi-session support allows controlling the number of concurrent devices per user - enforcing that workspace owners add employees as individual members rather than sharing a single account
- Auth UI is fully custom - Better Auth provides the API endpoints, Ordre builds the pages (multi-step registration, branded login, etc.)
- Only workspace members (owners, admins, and members) authenticate - clients access boards via a unique link and never create an account

**Who authenticates:** Every owner account and every member account (admin or member role) is a Better Auth user. Clients are excluded - they verify their identity via a one-time token sent by email (Resend) or SMS (Twilio), not through Better Auth.

**Alternatives considered:** Auth0 (industry standard with strong Canadian market recognition, 25,000 MAU free tier, but user data lives externally and MAU-based pricing at scale), Clerk (polished DX but higher per-MAU cost), AWS Cognito (rougher developer experience).

## 📱 SMS & WhatsApp - Twilio

**Status:** Chosen

**Why:**

- Industry-standard messaging API with excellent documentation and SDKs
- Covers board link delivery via SMS and WhatsApp, and client verification via SMS (4-digit token)
- WhatsApp Business API support is important for the Brazilian market where WhatsApp is the dominant channel
- Pay-per-message pricing with no minimum commitment
- Trial credit covers development and testing

**Use cases:**

| Message type                        | Channel         | Trigger                                                                |
| ----------------------------------- | --------------- | ---------------------------------------------------------------------- |
| Board link delivery                 | SMS or WhatsApp | Workspace member creates a new board                                   |
| Client verification (4-digit token) | SMS             | Client requests access to blurred fields (when email is not available) |
| Member notifications                | SMS             | Optional alerts (e.g. client approved a request)                       |

**Market consideration:** SMS costs vary significantly by country. Brazil is the most expensive of the three target markets. Defaulting to WhatsApp delivery for Brazilian clients reduces per-message cost substantially. The workspace member chooses the delivery channel when sharing the board link.

**Alternatives considered:** Plivo (cheaper per-message rates - strong alternative if Twilio costs grow at scale), AWS SNS (requires an AWS account, rougher DX, less mature WhatsApp support).

## ✉️ Email - Resend

**Status:** Chosen

**Why:**

- Developer-first email API built by the team behind React Email - natural fit for the React/Next.js stack
- Clean REST API and official Node.js SDK; templates can be authored as React components
- Free tier (3,000 emails per month) covers development and early production
- Handles both transactional email (verification tokens, password resets, board notifications) and marketing email (member onboarding sequences, product updates)

**Use cases:**

| Email type                          | Recipient | Trigger                                        |
| ----------------------------------- | --------- | ---------------------------------------------- |
| Board notification                  | Client    | New update, photo, or approval request posted  |
| Client verification (4-digit token) | Client    | Client requests access to blurred fields       |
| Transactional                       | Member    | Welcome email, password reset, account changes |
| Marketing                           | Member    | Onboarding tips, feature announcements         |

**Alternatives considered:** AWS SES (cheapest at scale but requires AWS account and minimal DX), SendGrid (legacy platform, removed free tier), Postmark (excellent deliverability but higher cost and no marketing email support on the same account).

## 🐛 Error Tracking - Sentry

**Status:** Release tracking wired in CI; SDK integration pending

**Why:**

- Industry standard for error tracking; strong portfolio signal
- Official Next.js SDK with 3-layer integration (client, server, edge)
- Automatic error grouping with full context (user, browser, breadcrumbs)
- GitHub integration to link errors to specific commits/releases
- Free tier is sufficient for development and beta

**Current setup:** A reusable `sentry.yml` GitHub Actions workflow publishes a Sentry release per app (via `getsentry/action-release`) as part of the deploy pipeline. The client/server SDKs themselves are not yet wired into the Next.js or React Router apps.

**Setup pattern:** Environment-based activation; source maps uploaded via CI to enable unminified stack traces.

## 📖 Component Documentation - Storybook

**Status:** Live and deployed

**Why:**

- Industry standard for component documentation and visual development
- Enables isolated component development - build and test UI components without running the full app
- Stories double as visual regression tests and design handoff artefacts
- Integrates with the existing `@ordre/ui` package structure - each component ships with a `.stories.tsx` file

**Hosting:** Deployed to `storybook.ordre.app` via Vercel as a static export.

**Scope:** Documents all components in `@ordre/ui`. App-specific components in `apps/*/src/shared/components/` are documented locally and not published to the shared Storybook.

**Process:** Every new component added to `@ordre/ui` ships with a `.stories.tsx` file alongside its implementation - there is no "add story later" path. Design tokens (colors, iconography) are documented via MDX pages in the same Storybook.

## 🔄 Future Compute Options

**Status:** Mapped as options, not committed

**Context:** Express is the deployed backend. If traffic patterns, cost, or infrastructure goals make a different compute model more attractive, the adapter pattern in `apps/api/` makes either migration low-effort - business logic in `logic/` is untouched in both cases.

### Option A - AWS Lambda + API Gateway

Each Express route becomes an individual Lambda handler. The handler extracts values from the Lambda `event` object, calls the same `logic/` function, and returns the Lambda response shape. API Gateway handles routing and CORS in place of Express.

**When to consider:** AWS skills are a priority for the portfolio, or pay-per-invocation pricing is more cost-effective at the actual traffic volume.

### Option B - Vercel Functions

Each Express route becomes a Vercel Function. The function signature changes from Express `(req, res)` to Vercel's standard `Request`/`Response` format, but calls the same `logic/` function. Routing is handled by Vercel natively - no separate API Gateway needed. Since Vercel already hosts all frontends, no additional vendor is introduced.

**When to consider:** Simplifying the infrastructure footprint; Vercel Functions are included in the Pro plan already paid for frontend hosting.

### What stays the same in either migration

- `logic/` business logic functions - untouched
- `@ordre/core` schemas and types
- `@ordre/services` data access layer
- Drizzle ORM schemas and migrations
- All other services (Upstash Redis, Auth0, Twilio, Resend, Sentry, Umami)

### Database portability note

Neon is standard PostgreSQL. If the database host ever needs to change, the switch is a driver swap and connection string change in Drizzle config - schemas, queries, and migrations are identical. Data migrates via standard `pg_dump`/`pg_restore`.

## 🔄 SMS Alternative - Plivo

**Status:** Mapped as a future option

**Why it's listed:** If Twilio costs grow significantly at scale (particularly due to Brazil SMS rates), Plivo is a drop-in alternative with lower per-message pricing and a similar REST API. The messaging layer should be abstracted behind a `NotificationService` interface in `@ordre/services` to make this swap straightforward.

**When to consider:** Twilio spend exceeds ~$200/month consistently, or Brazil SMS volume justifies negotiating rates.
