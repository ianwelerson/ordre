Environment config is split between **shared infrastructure** (things every app needs, like the database) at the repo root, and **app-specific** values inside each app. The API validates its variables with a Zod schema at startup, so a missing or malformed value fails immediately rather than at request time.

## The files

| File                     | Scope                        | Committed?                     | Purpose                                                     |
| ------------------------ | ---------------------------- | ------------------------------ | ---------------------------------------------------------- |
| `.env`                   | Shared infra (dev)           | No                             | Database connection strings used across apps                |
| `.env.example`           | Shared infra template        | Yes                            | Copy to `.env` and fill in                                  |
| `.env.test`              | Shared infra (test)          | No                             | Points at a **dedicated, disposable** test database         |
| `.env.test.example`      | Shared infra test template   | Yes                            | Copy to `.env.test`                                         |
| `apps/api/.env`          | API-specific (dev)           | No                             | Auth secret, stage, port, Resend key, app origins           |
| `apps/api/.env.example`  | API-specific template        | Yes                            | Copy to `apps/api/.env`                                     |
| `apps/api/.env.test`     | API-specific (test)          | No                             | API values used under `APP_STAGE=test`                      |

<Callout type="warn">
  The test harness `TRUNCATE`s every table before each test. Point `.env.test`
  at a database you are happy to wipe - never a database with real data.
</Callout>

## How they are loaded

The API's [`env.ts`](https://github.com/ianwelerson/ordre/blob/main/apps/api/src/config/env.ts) picks the stage from `APP_STAGE` (falling back to `NODE_ENV`, default `development`) and loads **root first, then app** so app values can override shared ones:

| Stage           | Files loaded (in order)                    |
| --------------- | ------------------------------------------ |
| `development`   | `../../.env` → `apps/api/.env`             |
| `test`          | `../../.env.test` → `apps/api/.env.test`  |
| `staging`       | none - variables come from the host        |
| `production`    | none - variables come from the host        |

On a deployed stage nothing is read from disk; the host (Railway, Neon, etc.) provides the variables directly.

<Callout type="warn">
  Turborepo only forwards variables it has been told about. A new API variable
  must be added to `globalEnv` in [`turbo.json`](https://github.com/ianwelerson/ordre/blob/main/turbo.json)
  as well as to the schema - otherwise it is present in the shell, absent inside
  the task, and the API fails startup validation for a variable you can see with
  `echo`.
</Callout>

## Shared infrastructure (`.env` / `.env.test`)

These live at the repo root because more than one package needs them (the API runtime and the Drizzle migration tooling).

| Variable             | Required | Example                                        | Notes                                                                    |
| -------------------- | -------- | ---------------------------------------------- | ------------------------------------------------------------------------ |
| `DATABASE_URL`       | yes      | `postgresql://ordre_app@localhost:5432/ordre`  | Runtime connection - the restricted `ordre_app` role                     |
| `DATABASE_OWNER_URL` | yes      | `postgresql://owner@localhost:5432/ordre`      | Migration connection - the table **owner** (see [Database Roles & RLS](/internal-docs/setup/database-roles)) |

Both are validated to start with `postgresql://`. The two-role split is what lets Row-Level Security actually enforce - see [Database Roles & RLS](/internal-docs/setup/database-roles).

## API-specific (`apps/api/.env`)

| Variable              | Required | Default         | Notes                                                                 |
| --------------------- | -------- | --------------- | --------------------------------------------------------------------- |
| `APP_STAGE`           | no       | `development`   | **Which deployment this is**: `development` \| `test` \| `staging` \| `production`. The one the app branches on |
| `NODE_ENV`            | no       | `development`   | **Whether to run optimized**: `development` \| `test` \| `production`. Must be `production` on a deployed stage (see below) |
| `PORT`                | no       | `3000`          | HTTP port for the raw server (`api:dev:app`)                          |
| `BETTER_AUTH_SECRET`  | yes      | -               | Session signing secret, min 32 chars.       |
| `RESEND_API_KEY`      | yes      | -               | Resend API key used by the outbox worker to deliver email. Required at startup on every stage - see [Transactional Outbox](/internal-docs/engineering/outbox) |
| `BETTER_AUTH_URL`     | yes      | -               | **The API's own public origin**, one per stage - `https://api.ordre.localhost` in dev, `https://api.staging.ordre.app`, `https://api.ordre.app`. Never a frontend's. |
| `APP_BASE_URL`        | yes      | -               | Marketing site origin - `https://ordre.localhost`, `https://staging.ordre.app`, `https://ordre.app` |
| `APP_DASHBOARD_URL`   | yes      | -               | Dashboard origin - `https://dashboard.ordre.localhost`, `https://dashboard.staging.ordre.app`, `https://dashboard.ordre.app` |
| `APP_BOARD_URL`       | yes      | -               | Board origin - `https://board.ordre.localhost`, `https://go.staging.ordre.app`, `https://go.ordre.app` |
| `APP_DOCS_URL`        | yes      | -               | Docs origin - `https://docs.ordre.localhost`, `https://docs.staging.ordre.app`, `https://docs.ordre.app` |

<Callout>
  The four `APP_*_URL` origins are not just for building links. `appOrigins` in
  `src/config/urls.ts` feeds both the CORS allowlist and Better Auth's
  `trustedOrigins`, so a frontend missing from here has its browser requests
  blocked rather than 404'd. Add the origin, don't widen CORS.
</Callout>

## `APP_STAGE` vs `NODE_ENV`

They answer different questions and are **not** required to match.

`APP_STAGE` is *which deployment this is*. It is the variable app code branches on,
and the only one that can tell staging from production. `NODE_ENV` is *whether to
run optimized* - the variable third-party tooling (Express, bundlers, `pino-pretty`,
pnpm's devDependency pruning) reads, and it has no `staging` value to offer.

So a staging deploy runs `APP_STAGE=staging` with `NODE_ENV=production`, and the
schema enforces exactly that: on any **deployed** stage (`staging`, `production`)
`NODE_ENV` must be `production`. Every other combination is left alone.

<Callout type="warn">
  On Railway, `NODE_ENV` is injected as `production` by the builder - leave it
  unset there and set only `APP_STAGE`.
</Callout>

Guards in [`env.ts`](https://github.com/ianwelerson/ordre/blob/main/apps/api/src/config/env.ts)
follow the same split: `isProd()`, `isStaging()`, `isDev()`, and `isTest()` test one
stage each, and `isDeployed()` is true on `staging` **and** `production`. Prefer
`isDeployed()` for anything staging must also honour - rate limits, webhook signature
checks, "don't send this to a real customer" fuses.
