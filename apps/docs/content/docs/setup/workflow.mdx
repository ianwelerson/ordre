Three mechanisms shape every change: hooks that run before a commit is written, a
convention the commit message has to satisfy, and a merge strategy that keeps the
history readable.

## Pre-commit hooks

[Husky](https://typicode.github.io/husky/) installs two git hooks, and
[lint-staged](https://github.com/lint-staged/lint-staged) decides what runs based
on which files are staged.

| Staged files | What runs | Tools |
| ------------ | --------- | ----- |
| `*.{js,ts,tsx}` | `pnpm lint` and `pnpm format:check` | ESLint, Prettier |
| `*.{ts,tsx}` | `pnpm check-types` | TypeScript |
| `package.json` | `pnpm packages:lint` | Syncpack |
| `apps/api/**` | `pnpm api:docs:generate`, then stages the result | The OpenAPI generator |

The commands are deliberately **repo-wide** rather than scoped to the staged files.
Turborepo caches them, so the second run is nearly free, and a change in one
workspace that breaks the types of another is caught at the commit rather than in
CI.

The last row is the one worth knowing about: touching the API regenerates
`apps/docs/public/openapi.json` and adds it to the same commit, so the published
API reference can never describe a contract that is not in the tree.

<Callout>
  The `commit-msg` hook runs commitlint against the message described below. It
  rejects the commit rather than rewriting it, so a malformed message costs a
  retry, not a lost change.
</Callout>

## Commit messages

All commits follow [Conventional Commits](https://www.conventionalcommits.org/):

```
type(scope): message
```

**Types**, enforced by `commitlint.config.ts`:

| Type | For |
| ---- | --- |
| `feat` | A new capability |
| `fix` | A defect repair |
| `refactor` | A change that alters structure but not behaviour |
| `perf` | A change made for speed or resource use |
| `test` | Tests only |
| `docs` | Documentation only |
| `style` | Formatting only, no code meaning changed |
| `build` | Build system or dependencies |
| `ci` | CI configuration |
| `chore` | Housekeeping that fits nothing above |
| `setup` | Project scaffolding |
| `revert` | Undoing an earlier commit |

The **scope** is the workspace the change lands in: `dashboard`, `api`, `ui`,
`core`, `db`, and so on.

```
feat(dashboard): add member invite flow
fix(api): trust both proxy hops
chore: update dependencies
```

No AI attribution trailers. See
[AI Assistance](/internal-docs/engineering/ai-assistance).

## Merging

**Rebase and merge**, so the history stays linear and every commit is a logical,
atomic change.

- Rebase a feature branch onto `develop` before merging.
- No merge commits.
- Review focuses on the final shape of the diff, not the path taken to reach it.

`develop` is the integration branch and deploys to the develop environment;
`main` is production, and a tag on it triggers the production deploy. See the
[workflows in `.github/workflows`](https://github.com/ianwelerson/ordre/tree/main/.github/workflows)
for what each event runs.

## Before you push

CI runs lint, type-check, and both test tiers on every pull request. To get the
same answer locally:

```bash
pnpm lint
pnpm check-types
pnpm test:unit:ci
```

The full script list is in
[Running the Project](/internal-docs/setup/running-the-project#common-root-scripts),
and what the two test tiers own is in [Testing](/internal-docs/engineering/testing).
