Everything here is committed for the initial release. The page opens with the
order the work is being done in, then lists the full scope grouped by layer - the
product features clients and members see, the API that powers them, the apps that
ship them, the foundations underneath, the platform they run on, and the
commercial layer. The **Status** column shows where each piece stands today.
There are no dates or deadlines; the order is a sequence, not a schedule.

**Status key:** ✅ Done · 🚧 In progress · 📋 Planned

## The order of work

Grouping by layer is how you find something on this page, not how it gets built.
The build order follows one rule: work whose cost rises the longer it waits goes
first. A change to an API contract is nearly free while no screen consumes it and
a breaking change once one does, so contract changes land ahead of the screens
that will depend on them. The same logic puts a few pieces of security and
logging work early, next to the features they protect, rather than in a cleanup
phase at the end.

### In progress: creating an account

The last unbuilt part of the signed-out product. Someone invited into an existing
workspace can already complete the whole flow; what is missing is creating a
workspace from nothing. That flow collects the industry, the kind of provider, a
name, an optional business name, the workspace address, contact details and a
password, then creates the account and the workspace together.

Three things ship alongside it. The screen that confirms an email address, which
is what allows a verified address to become a requirement rather than a
suggestion. A way to turn down an invite meant for somebody else. And request
limits on the public endpoints this flow leans on, since checking whether a
workspace address is free is a question anyone can ask without an account.

### Next: the workspace behind the session

Everything that requires a sign-in. The shell comes first, because it decides
where the current workspace and location live for every screen after it, followed
by the home screen it lands on, then team management, workspace settings and
personal settings.

Most of this is interface work: the API already covers every action on the team
screen and nearly all of workspace settings. One API change comes first, though,
because it gets expensive later - every list endpoint gains a consistent envelope
for paging before any screen starts reading one.

### Then: boards

The product itself, and the largest block of work on this page. It starts with a
design question rather than code: clients reach a board through a link and never
create an account, so none of the existing access rules describe them. Settling
how a board decides what a link-holder may see comes before the schema, the
tokens, and the client-facing read model that depend on it.

The API arrives first - boards, clients, templates, the timeline, approvals,
photos, chat, verification and recurring visits - then the screens on both sides:
the member's working view in the dashboard, and the board the client opens.

### Finally: opening the doors

Subscription billing with localised pricing and the public marketing site. Ahead
of either, the backend and database move onto their production plans, which is
the point several of the foundations below are working towards.

The switches that close a surface without a deploy are built, and the API
enforces each one. See
[Feature Switches](/internal-docs/architecture/feature-switches).

## Product

| Identity verification      | Sensitive fields blurred until the client verifies via email or phone                                                                                                                                                                                                                   | 📋     |

<Callout title="Boards update on load, not live">
  A board reflects its timeline as of the moment it was loaded. Pushing changes to an open board is
  deliberately out of launch scope; a board changes a handful of times a day, and the infrastructure
  to fan those changes out is far easier to add to a working product than to carry through one that
  doesn't exist yet. It's captured in [Ideas](/internal-docs/product/roadmap/ideas).
</Callout>

### Dashboard screens

The signed-out surface is built; everything behind a session is still to come.
Each screen is a view under `src/views/`, with its route in `src/app/(auth)/` or
`src/app/(authenticated)/`.

| Screen                               | Description                                                                                                                                             | Status |
| ------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------- | ------ |
| Route gate (`src/proxy.ts`)          | Picks the auth shell or the app shell per request; carries the intended destination through `?next=`                                                    | ✅     |
| Sign in (`/login`)                   | Email and password, keep-me-signed-in, arrival notices, and the `?next=` round trip                                                                     | ✅     |
| Forgot password (`/forgot-password`) | Requests the reset mail and swaps itself for the confirmation; reveals nothing about the address                                                        | ✅     |
| Set password (`/set-password`)       | Serves both the reset and the invite's first password, plus the expired-link dead end                                                                   | ✅     |
| Invite (`/invite/:token`)            | Preview, sign-up-and-join, one-click join for a signed-in invitee, wrong-account, and error states                                                      | ✅     |
| Decline an invite                    | The API endpoint is live; the dashboard has no "not you?" action yet                                                                                    | 📋     |
| Registration (`/get-started`)        | Placeholder screen. `/register` redirects here from `next.config.ts`. The flow in [Specs](/internal-docs/product/specs) is designed and being built now | 🚧     |
| Sign-in link (magic link)            | Drafted on the login screen and commented out pending the API endpoint                                                                                  | 📋     |
| Email verification                   | The screen that lets a verified address become a precondition for workspace actions                                                                     | 📋     |

Behind the session, the shell and the four screens whose APIs are already complete
come first; the board screens follow the Board API.

| Screen             | Description                                                                                      | Status |
| ------------------ | ------------------------------------------------------------------------------------------------ | ------ |
| Shell & navigation | Sidebar, workspace switcher, location switcher, notifications                                    | 📋     |
| Home               | Workspace activity at a glance; empty until boards exist                                         | 📋     |
| Team               | Member list, invites, role changes, removal. The API covers every action on this screen          | 📋     |
| User settings      | Profile and locale. Notification and working-hours preferences need tables that aren't built yet | 📋     |
| Workspace settings | General, branding, and locations. Services, plan, channels, and templates arrive with their APIs | 📋     |
| Boards             | List, creation, and the member-side board detail                                                 | 📋     |
| Clients & messages | Client records and board-scoped conversations                                                    | 📋     |

The five built screens share one anatomy - `AuthCard`, `AuthHeading`, `AuthAction`,
`AuthFootnote` in `src/shared/components/` - so the card width, the spacing rhythm
and the primary action are decided once rather than per screen.

## Foundations

Work that sits under every feature rather than inside one. It appears here because
it takes real time and because several pieces are preconditions for running the
product in production rather than optional polish.

| Area                | What it covers                                                                                                     | Status |
| ------------------- | ------------------------------------------------------------------------------------------------------------------ | ------ |
| Feature switches    | Global switches closing sign-in, sign-up, workspace creation, locations and invites without a deploy               | ✅     |
| Log hygiene         | Session cookies, invite tokens and query parameters scrubbed from every log record                                 | ✅     |
| Process resilience  | Dropped database connections and uncaught failures handled rather than ending the process                          | ✅     |
| Invite privileges   | An administrator cannot issue an invite that grants more than they hold                                            | ✅     |
| Rate limiting       | Request limits on the public endpoints: sign-in, sign-up, password reset, invites, and the workspace address check | 📋     |
| Email verification  | A confirmed address as a precondition for acting inside a workspace                                                | 📋     |
| List paging         | One envelope and one cursor convention across every list endpoint                                                  | 📋     |
| Request correlation | An id on every request, joining its access log line to any error it produced and returned to the caller            | 📋     |
| Error reporting     | A single place unexpected failures pass through, so an error tracker plugs in once rather than per handler         | 📋     |
| Database backstop   | Suspended members excluded by the database itself, not only by the application                                     | 📋     |
| Production capacity | Connection limits and transaction scope chosen deliberately rather than inherited from defaults                    | 📋     |
