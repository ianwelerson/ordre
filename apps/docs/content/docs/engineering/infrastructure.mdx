## 🚀 Frontend Hosting - Vercel

**Status:** Chosen and active

**Why:**

- Purpose-built for Next.js (made by the same team); zero-config deployments
- Native App Router support and Turbopack optimizations
- Automatic preview deployments per PR; easy environment variable management
- Industry-standard choice for Next.js projects; strong portfolio signal
- Free Hobby tier covers development; Pro tier when monetised

**Plan:** Hobby (free) during development. Pro ($20/month flat, unlimited team members) once Ordre is commercial. The Pro plan's included bandwidth and serverless compute are more than sufficient for early production.

**Tradeoff accepted:** Some Vercel-specific features exist, but the core app is standard Next.js and remains portable.

## 🚂 Backend Compute - Railway

**Status:** Chosen

**Why:**

- Usage-based billing (per-second) - pay for actual CPU and RAM consumed, not reserved capacity
- Vertical auto-scaling: the container uses more resources under load and scales back down at idle, automatically
- Long-running process support - Express runs as a persistent server, which is what keeps a warm connection pool, an interactive transaction per request, and the outbox worker inside the same process
- Git-connected deploys from GitHub with preview environments per PR
- Excellent CLI tooling for local development and deployment
- Hobby plan ($5/month, includes $5 usage credit) covers development and early production

**How it works:** Express runs as a containerised service on Railway. Under low traffic (e.g. overnight), the container idles at minimal CPU/RAM and the cost drops proportionally. During active hours, it scales up automatically - no configuration needed, no tier jumps. At the plan limits (8 vCPU, 8 GB RAM on Hobby), upgrading to Pro ($20/month per seat, includes $20 credit) raises the ceiling to 32 vCPU / 32 GB RAM and enables horizontal scaling via replicas.

**Environments:**

| Environment | Plan                        | Behaviour               | `APP_STAGE`  |
| ----------- | --------------------------- | ----------------------- | ------------ |
| Production  | Hobby ($5/month)            | Always-on, auto-scaling | `production` |
| Staging     | Free ($1/month after trial) | Scale-to-zero when idle | `staging`    |

Both run with `NODE_ENV=production` - Railway's builder injects it, and the API's schema requires it on a deployed stage. `APP_STAGE` is the variable that tells the two apart; see [Environment Variables](/internal-docs/setup/environment-variables#app_stage-vs-node_env).

The service's exact configuration (skipped build, direct `node` start command, V8 heap cap) is documented in [Setup - API Deployment](/internal-docs/setup/deployment) - it exists only in the Railway dashboard, and that page is its record.

**Alternatives considered:** Render (fixed tier pricing - $7 Starter with steep jumps to $25/$85; less cost-efficient at scale), Fly.io (removed free tier), Heroku (expensive for equivalent resources), self-managed VPS (operational overhead).

## 💾 Database - Neon

**Status:** Chosen

**Why:**

- Serverless PostgreSQL with true scale-to-zero - no idle instance cost during low-traffic periods or overnight
- Ordre's data is relational by nature - boards, workspaces, members, clients, updates, approvals
- Database branching for isolated dev/staging environments at no extra cost
- Drizzle ORM abstracts the driver - standard PostgreSQL throughout, fully portable via `pg_dump`/`pg_restore`
- Free tier (0.5 GB storage, 100 compute-hours per month) covers development and early production through ~100 owners

**Plan progression:** Free tier → Launch ($19/month, 10 GB, 300 CU-hours) → Scale ($69/month, 50 GB, 750 CU-hours) as usage grows.

**Data retention:** Active boards and archived boards are both stored with full history. Old boards remain accessible to clients via their original link.

**Connection management:** The API connects through node-postgres (`pg`) with a single shared connection pool, created once per process in `apps/api/src/config/db.ts`. Because the API is a long-lived Express process on Railway (not serverless), a warm pool is the right model - it reuses TCP connections across requests and enables interactive transactions, neither of which Neon's HTTP driver offers. The pool is drained on `SIGTERM`/`SIGINT` so deploys and restarts finish in-flight queries before exiting. It also carries an `'error'` listener, because `pg` emits that event on an idle pooled client whose connection the server dropped, which is what a Neon restart or failover looks like from the API's side. `Pool` is an `EventEmitter`, so an unhandled `'error'` throws and ends the process with nothing in the log to explain it. The listener records the failure under `event: 'db.pool_error'` and does nothing else: `pg` has already discarded the dead client, and the next request opens a fresh connection. In production, `DATABASE_URL` points at Neon's pooled endpoint (the `-pooler` host) with `sslmode=verify-full`, stated explicitly so that certificate and hostname verification survives the `pg` 9 change that gives `sslmode=require` libpq semantics; local development uses a Homebrew PostgreSQL instance with a password-less, SSL-free connection string.

**Alternatives considered:** AWS RDS PostgreSQL (always-on instance cost, AWS account required), Supabase (opinionated all-in-one stack), Aurora Serverless v2 (high minimum cost at low scale - 0.5 ACU floor).

## 📷 Image Storage - Cloudflare R2

**Status:** Chosen

**Why:**

- S3-compatible object storage with zero egress fees at any volume - images are served globally through Cloudflare's 330+ edge locations at no transfer cost
- Already using Cloudflare for DNS on `ordre.app` - R2 is in the same dashboard, same account
- Free tier (10 GB storage, 1 million writes, 10 million reads per month) covers development and early production with no expiration
- No separate CDN needed - Cloudflare's global network acts as the CDN automatically
- The AWS SDK and any S3-compatible library work with R2 via a config change (endpoint URL + credentials)

**Upload flow:** Workspace members upload photos via a pre-signed URL generated by the Express API. No file data passes through the API - the client uploads directly to R2.

**Image processing:** Thumbnails for timeline views are generated on upload to reduce transfer size. Full-resolution originals are served on click. Both are stored in R2.

**Alternatives considered:** AWS S3 + CloudFront (egress fees dominate at scale), Railway Object Storage (same storage price but charges egress with no CDN), Backblaze B2 (cheaper storage but requires Cloudflare CDN integration for free egress).

## 🔐 Authentication - Better Auth

**Status:** Chosen

**Why:**

- Open-source library that runs directly inside the Express app - no external service, no MAU pricing, no lock-in
- Session-based authentication with auth data stored in the Neon database alongside app tables
- Handles password hashing, session management, CSRF protection, and rate limiting out of the box
- Multi-session support allows controlling the number of concurrent devices per user - enforcing that workspace owners add employees as individual members rather than sharing a single account
- Auth UI is fully custom - Better Auth provides the API endpoints, Ordre builds the pages (multi-step registration, branded login, etc.)
- Only workspace members (owners, admins, and members) authenticate - clients access boards via a unique link and never create an account

**Who authenticates:** Every owner account and every member account (admin or member role) is a Better Auth user. Clients are excluded - they verify their identity via a one-time token sent by email (Resend) or SMS (Twilio), not through Better Auth.

**Alternatives considered:** Auth0 (industry standard with strong Canadian market recognition, 25,000 MAU free tier, but user data lives externally and MAU-based pricing at scale), Clerk (polished DX but higher per-MAU cost), AWS Cognito (rougher developer experience).

### Better Auth Dash

**Status:** Trialling

`@better-auth/infra` ships a `dash()` plugin that connects the API to Better Auth's
hosted dashboard: user administration, session inspection and revocation, and sign-up
and sign-in history. It reads the `user`, `session`, and `account` tables through the
same Drizzle adapter the app uses, so the records stay in Neon.

It is mounted only when a key is configured, in `apps/api/src/config/auth.ts`:

```ts
const dashPlugins = env.BETTER_AUTH_API_KEY ? [dash({ apiKey: env.BETTER_AUTH_API_KEY })] : [];
```

The key is passed explicitly rather than left to the plugin's own `process.env` read,
so the value reaching it is the one the Zod schema validated. An environment without
a key, which includes every test run, mounts nothing.

<Callout type="warn">
  The plugin sends auth **events** - sign-ups, sign-ins, session lifecycle - to Better Auth's API as
  they happen. The rows stay in Neon, the activity metadata does not. That is the trade being made
  for the dashboard, and it is why the plugin is opt-in per environment rather than always on.
</Callout>

Keeping it conditional is what preserves the "no lock-in" claim above. `dash()` adds no
columns unless `activityTracking` or `managedDirectorySync` is enabled, and neither is,
so backing it out is deleting the const and its spread - no migration to unwind.

#### `sentinel` evaluated, not adopted

The same package ships a security plugin covering breached-password rejection,
disposable-email blocking, bot and geo blocking, velocity limits, impossible-travel
detection, and device-keyed abuse prevention.

Its device-level checks depend on the Better Auth **client** SDK, which fingerprints
the browser and posts the record to Better Auth's KV so the server can load it back.
The dashboard reaches the API through `@ordre/services`' own fetch client instead, so
no identification record is ever created and the server resolves no visitor id. The
consequences are not uniform degradation:

| Check                                                  | Without a visitor id                 |
| ------------------------------------------------------ | ------------------------------------ |
| `compromisedPassword`, `emailValidation`, `staleUsers` | Work - evaluated server-side         |
| `credentialStuffing`, `velocity`                       | Fall back to email and IP keying     |
| `impossibleTravel`, `maxSignupsPerVisitor`             | Silently skipped                     |
| Any `action: 'challenge'`                              | Degrades to allow                    |
| `freeTrialAbuse`                                       | **Rejects every sign-up with a 403** |

What still works costs two external round trips on the sign-in path and a deeper
runtime dependency on the hosted service. Revisit only alongside a decision to adopt
the Better Auth client. If it is ever enabled, `emailNormalization` must stay off: it
rewrites addresses past lowercasing, which would break the invite address match in
`apps/dashboard/src/views/Invite/model/useInviteState.ts`.

## ✉️ Email and audience - Resend

**Status:** Live - integrated and delivering

**Why:**

- Developer-first email API built by the team behind React Email - natural fit for the React/Next.js stack
- Clean REST API and official Node.js SDK. Templates are ours, written with React Email in `packages/email` and rendered on each send, so a message is versioned with the code that sends it
- Free tier covers development and early production
- Handles both transactional email (account and workspace lifecycle, invitations, board notifications) and marketing email (member onboarding sequences, product updates)

**How it's wired:** the API never calls Resend from a request. A producer writes a row to the `outbox` table inside the same transaction as the business data, and a background worker claims and delivers it. That is what keeps a request DB-only and makes a Resend outage a retry rather than a failed sign-up. Two channels share that queue: `email` sends a rendered message, `audience` keeps the contact record and its segments in step with workspace membership. See **[Transactional Outbox](/internal-docs/engineering/outbox)** for the full design.

**Delivering today:**

| Topic               | Recipient       | Trigger                             |
| ------------------- | --------------- | ----------------------------------- |
| `account:created`   | New user        | A Better Auth user row is created   |
| `workspace:created` | Workspace owner | A workspace is created              |
| `invite:created`    | Invited person  | An admin creates a workspace invite |

**Syncing today** (the `audience` channel, one delivery):

| Topic          | Contact           | Trigger                                                                 |
| -------------- | ----------------- | ----------------------------------------------------------------------- |
| `contact:sync` | The account owner | Sign-up, workspace creation, invite accept, role change, removal, leave |

Segments are ours - `all-accounts`, `workspace-owner`, `workspace-member` - and each
row carries the complete set, so the provider reconciles against what Resend holds.
Topics are the contact's: `product-news` and `workspace-updates`, opted into and
never opted out of by us. Ids are per environment and come from `RESEND_SEGMENT_*` /
`RESEND_TOPIC_*`; a row names them, never their ids.

**Planned:** board notifications (new update, photo, approval request) and client verification tokens land as new outbox topics once boards exist, and reuse the same worker.

<Callout type="warn">
  **Free-plan rate limits are load-bearing.** The plan caps daily sends, so the worker treats a
  Resend `429` as "not this message's fault": the attempt is handed back and the row waits an hour
  instead of burning a retry. Confirm the current cap against the [Resend pricing
  page](https://resend.com/pricing) before assuming headroom for a bulk send.
</Callout>

<Callout type="warn">
  **One API key serves every environment today**, and `DISABLE_OUTBOX_EMAIL` skips email only. A
  local sign-up therefore writes a real contact into the account's audience. Point a local `.env` at
  throwaway segment ids until the keys diverge: a broadcast targets a segment, so a contact in a
  dev-only segment can never be reached by one.
</Callout>

**Sending domain:** `ordre.app`, verified with Resend. The from-address is a constant rather than an env-derived origin - there is no `@ordre.localhost` to send from - so dev, staging, and production all send as the same verified sender. The **links inside** the email are environment-specific and come from `config/urls.ts`.

**Alternatives considered:** AWS SES (cheapest at scale but requires AWS account and minimal DX), SendGrid (legacy platform, removed free tier), Postmark (excellent deliverability but higher cost and no marketing email support on the same account).

## 📋 Logging - pino, with a deferred platform

**Status:** Structured logging active; managed platform deferred

**Logging (active):** Application and HTTP logs go through [pino](https://github.com/pinojs/pino), configured once in the `@ordre/monitoring` package - `createLogger` for application logs (the `console.log` replacement) and `httpLogger` (pino-http) for Express access logs. Output is pretty-printed in development and raw JSON in production, with secret redaction applied centrally. Each service tags its logs with a `service` field so they remain queryable per app once centralised. See [Architecture](/internal-docs/engineering/architecture) → `@ordre/monitoring` for the package design.

**Process-level failures:** The API entrypoint registers `uncaughtException` and `unhandledRejection` handlers, so a crash is written to the structured log instead of landing on stderr outside it. `uncaughtException` logs at `fatal` under `event: 'process.uncaught_exception'` and then exits 1, because the process is in an unknown state and must not keep serving. `unhandledRejection` logs at `error` under `event: 'process.unhandled_rejection'` and keeps the process up, since one stray promise is not grounds for dropping every other in-flight request. The cost of that choice is that registering the listener disables Node's default of crashing on an unhandled rejection, which makes the event worth an alert once logs are centralised. The `fatal` line survives the immediate `process.exit(1)` in both output modes, because pino registers an `exit` handler that flushes synchronously: on the SonicBoom destination in production, and on the transport thread in development.

**Platform (deferred):** Shipping those JSON logs to a managed platform - Better Stack or Axiom - for retention, full-text search, and uptime alerts is deferred. Railway's and Vercel's built-in logs plus Sentry are sufficient during the early phase. Because pino already emits structured JSON tagged by service, adopting a platform later is a config change inside `@ordre/monitoring`, not an app-wide rewrite. Revisit once real traffic patterns and debugging needs emerge.

## 🔄 Future Compute Options

**Status:** Mapped as options, not committed

**Context:** Express is the deployed backend. If traffic patterns, cost, or infrastructure goals make a different compute model more attractive, the adapter pattern in `apps/api/` makes either migration low-effort - business logic in `logic/` is untouched in both cases.

### Option A - AWS Lambda + API Gateway

Each Express route becomes an individual Lambda handler. The handler extracts values from the Lambda `event` object, calls the same `logic/` function, and returns the Lambda response shape. API Gateway handles routing and CORS in place of Express.

**When to consider:** AWS skills are a priority for the portfolio, or pay-per-invocation pricing is more cost-effective at the actual traffic volume.

### Option B - Vercel Functions

Each Express route becomes a Vercel Function. The function signature changes from Express `(req, res)` to Vercel's standard `Request`/`Response` format, but calls the same `logic/` function. Routing is handled by Vercel natively - no separate API Gateway needed. Since Vercel already hosts all frontends, no additional vendor is introduced.

**When to consider:** Simplifying the infrastructure footprint; Vercel Functions are included in the Pro plan already paid for frontend hosting.

### What stays the same in either migration

- `logic/` business logic functions - untouched
- `@ordre/core` schemas and types
- `@ordre/services` data access layer
- Drizzle ORM schemas and migrations
- All other services (Upstash Redis, Better Auth, Twilio, Resend, Sentry, Umami)

### Database portability note

Neon is standard PostgreSQL. If the database host ever needs to change, the switch is a driver swap and connection string change in Drizzle config - schemas, queries, and migrations are identical. Data migrates via standard `pg_dump`/`pg_restore`.

The coupling runs the other way too: the `pg` pool driver is chosen specifically because the API is a long-lived process. Moving to a serverless compute model (Option A or B above) would mean swapping the client for Neon's serverless/HTTP driver, which is built for environments that can't hold a pooled TCP connection open - schemas and migrations stay the same, only `@ordre/db/connection` changes.

## 🔄 SMS Alternative - Plivo

**Status:** Mapped as a future option

**Why it's listed:** If Twilio costs grow significantly at scale (particularly due to Brazil SMS rates), Plivo is a drop-in alternative with lower per-message pricing and a similar REST API. The messaging layer should be abstracted behind a `NotificationService` interface in `@ordre/services` to make this swap straightforward.

**When to consider:** Twilio spend exceeds ~$200/month consistently, or Brazil SMS volume justifies negotiating rates.
