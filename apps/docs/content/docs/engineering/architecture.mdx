## 📁 Monorepo Root

```
ordre/
├── apps/                     # Runnable applications
│   ├── api/                  # Backend API (Express)
│   ├── dashboard/            # Dashboard Next.js app (workspace members)
│   ├── marketing/            # Marketing Next.js app
│   ├── portal/               # [FUTURE] Client portal Next.js app
│   ├── board/                # Board (shareable board) React app
│   ├── docs/                 # Guides + generated API reference (Fumadocs)
│   └── storybook/            # Component documentation
│
├── packages/                 # Shared, reusable code
│   ├── core/                 # Schemas, types, error catalog & every translated string
│   ├── db/                   # Database schema, migrations & connection
│   ├── services/             # HTTP client layer for the frontend apps
│   ├── monitoring/           # Structured logging (pino) & future error tracking
│   ├── ui/                   # Design system & components
│   └── config/               # Shared tooling configs
│
├── turbo.json                # Turborepo pipeline config
├── pnpm-workspace.yaml       # Workspace definition
└── package.json              # Root dependencies
```

**Rule:** `apps/` = things that run. `packages/` = things that are shared.

## 🧰 Shared Tech Stack

Every workspace sits on the same base, so the per-workspace sections below list
only what is specific to them.

| Concern      | Choice                                                                         |
| ------------ | ------------------------------------------------------------------------------ |
| Language     | TypeScript, strict, via `@ordre/config/typescript/*`                           |
| Monorepo     | Turborepo + pnpm workspaces                                                    |
| Runtime      | Node.js 24+ (see `.nvmrc`)                                                     |
| Testing      | Vitest, with `@vitest/coverage-v8`                                             |
| Linting      | ESLint 9 flat config, via `@ordre/config/eslint/*`                             |
| Formatting   | Prettier with import sorting, via `@ordre/config/prettier`                     |
| Dependencies | Syncpack, keeping shared versions aligned (`pnpm packages:lint`)               |
| Local HTTPS  | portless - see [Running the Project](/internal-docs/setup/running-the-project) |

Frontend workspaces add React 19, Tailwind CSS v4, and Testing Library with
Playwright as Vitest's browser provider.

<Callout>
  **Major versions only, on this page.** Exact versions live in each workspace's `package.json` and
  in `pnpm-lock.yaml` - a number copied into prose goes stale on the next dependency bump.
</Callout>

## 📦 Package Architecture

The packages follow a strict dependency flow. Upper layers may import from lower layers. **Lower layers must never import from upper layers**, and no package imports an app.

```
┌──────────────────────────────────────────────────────────┐
│                      Frontend Apps                       │
│              dashboard · board · marketing               │
└──────────────────────────┬───────────────────────────────┘
                           │
              ┌────────────┴────────────┐
              ▼                         ▼
┌─────────────────────┐   ┌────────────────────────────────┐
│      @ordre/ui      │   │        @ordre/services         │
│ Components, tokens, │   │      HTTP client layer         │
│  the form mechanism │   │                                │
└─────────────────────┘   └────────────────────────────────┘


┌──────────────────────────────────────────────────────────┐
│                         apps/api                         │
│ imports @ordre/db, @ordre/email, monitoring, @ordre/core │
└──────────────────────────┬───────────────────────────────┘
                           │
       ┌───────────────────┼───────────────────┐
       ▼                   ▼                   ▼
┌──────────────────┐ ┌───────────────┐ ┌────────────────────┐
│ @ordre/monitoring│ │ @ordre/email  │ │     @ordre/db      │
│   pino logging   │ │ React Email   │ │ Drizzle tables,    │
│                  │ │ templates.    │ │ migrations.        │
│                  │ │ Built, not    │ │ Only imported by   │
│                  │ │ raw source    │ │ apps/api           │
└──────────────────┘ └───────┬───────┘ └─────────┬──────────┘
                             │                   │
                             └─────────┬─────────┘
                                       ▼
┌──────────────────────────────────────────────────────────┐
│                       @ordre/core                        │
│             schemas · types · errors · enums             │
│           constants · permissions · messages             │
│             The floor: no Drizzle, no React.             │
│         Imported by every app and every package.         │
└──────────────────────────────────────────────────────────┘

  @ordre/config  -  devDependency of every workspace that has its own
                    ESLint/TypeScript config; ships no runtime code
```

The edges above are the real ones today, not the intended end state:

| Workspace                                                      | Depends on                                                                     |
| -------------------------------------------------------------- | ------------------------------------------------------------------------------ |
| `apps/api`                                                     | `@ordre/core`, `@ordre/db`, `@ordre/email`, `@ordre/monitoring`                |
| `apps/dashboard`                                               | `@ordre/core`, `@ordre/services`, `@ordre/ui`                                  |
| `apps/board` · `marketing`                                     | `@ordre/core`, `@ordre/ui`                                                     |
| `apps/docs`                                                    | `@ordre/core` (the error-code page is generated from its catalog and its copy) |
| `apps/storybook`                                               | `@ordre/ui`                                                                    |
| `@ordre/db` · `@ordre/services` · `@ordre/ui` · `@ordre/email` | `@ordre/core`                                                                  |
| `@ordre/core` · `monitoring`                                   | nothing but `@ordre/config`                                                    |
| `@ordre/config`                                                | nothing at all                                                                 |

`apps/storybook` carries no `@ordre/config` because it has no ESLint or TypeScript
config of its own - it lints through the workspaces it loads stories from.

Every workspace that renders anything sits on `@ordre/core`, because that is
where the strings live as well as the contract. Core has no React and no Drizzle,
so the edge stays legal from all of them.

Two rules fall out of that shape and are worth stating explicitly:

- **`@ordre/db` is imported by `apps/api` and nothing else.** No frontend, and not `@ordre/core`. Drizzle and `pg` stay out of every browser bundle.
- **`@ordre/core` is the floor.** It has no Drizzle and no React dependency, which is what lets both the API and the frontends import it.
- **`@ordre/email` is imported by `apps/api` and nothing else**, for the same reason as `@ordre/db`: it pulls in `react-dom/server`, which has no business in a browser bundle. It is also the only workspace consumed as **built output** rather than raw source, because it is the only one containing JSX - see [The API Runtime](/internal-docs/engineering/runtime).

<Callout>
  **`@ordre/core` holds every translated string - error copy, validation copy, email copy, and
  shared product words. That is a deliberate widening: the copy for an error is keyed by the same
  `ErrorCode` the catalog defines, and splitting the two across packages meant either duplicating
  strings or resolving them across a boundary that `errorResponse` could not cross. One package, one
  vocabulary.
</Callout>

## 🔍 Package Responsibilities

### `@ordre/core`

**Purpose:** The floor. Everything both sides of the wire have to agree on - schemas, types, error codes, route paths, permissions - plus every translated string in the product.

**Tech stack:** Zod 4 only. No Drizzle, no React - that is what keeps it importable by anything.

**Export paths:**

| Path                              | Contents                                                                                               |
| --------------------------------- | ------------------------------------------------------------------------------------------------------ |
| `@ordre/core/schemas`             | Zod schemas for request and response validation, plus `z` itself                                       |
| `@ordre/core/types`               | TypeScript types inferred from schemas, plus primitives (`ErrorDefinition`, `ErrorMap`, `StatusCodes`) |
| `@ordre/core/errors`              | Error catalogs, `ERROR_CATALOG`, `ErrorCode`, `ServiceError`, `errorResponse`                          |
| `@ordre/core/enums`               | Canonical value lists, several of which back Postgres enums                                            |
| `@ordre/core/constants`           | Values identical in every environment - route paths, TTLs, cookie names                                |
| `@ordre/core/permissions`         | The role/permission matrix and `can()`                                                                 |
| `@ordre/core/messages`            | Every translated string - `{ app, en, pt }`                                                            |
| `@ordre/core/messages/en` · `/pt` | One locale on its own                                                                                  |

**Key constraint:** No Drizzle dependency. No React dependency. Importable by any app - API, dashboard, board, or marketing.

#### Errors

Grouped by domain and keyed by a stable identifier. A definition carries **only a status** - the words live in [Messages](#messages), keyed by the same code.

```ts
import { errorMessage, VALIDATION_ERRORS } from '@ordre/core/errors';

VALIDATION_ERRORS.INVALID_INPUT; // { status: 400 }
errorMessage('INVALID_INPUT'); // "Some of the information you entered isn't valid."
```

`ERROR_CATALOG` merges every domain map into one object and `ErrorCode` is its `keyof`. That union is what types the copy as `Record<ErrorCode, string>`, so a code cannot ship without words for it in every locale. `CLIENT_ERRORS` (`NETWORK_ERROR`, `MALFORMED_RESPONSE`, `UNKNOWN_ERROR`) sit in the same catalog even though the server never returns them, so a consumer maps a dropped connection and a `403` through one vocabulary.

**One string per code.** `errorResponse` fills the wire `message` from the English copy, so a log line or a `curl` stays readable; a client ignores it and resolves the same code in the reader's own locale. The message is a courtesy, the code is the contract.

Every code, its status and its copy: **[Error Codes](/internal-docs/reference/error-codes)**, generated from the catalog.

#### Schemas and validation

Schemas carry **no messages at all** - `z.email()` stays `z.email()`. A global Zod error map, installed on import of `@ordre/core/schemas`, turns each issue into a stable key:

```ts
z.email()          →  "validation.email"
z.string().min(1)  →  "validation.required"
z.uuid()           →  "validation.uuid"
```

One schema is parsed in three places that need three different renderings: the browser (the user's locale), the API (which puts the key in `details` for a client to resolve), and the OpenAPI reference (English prose, resolved by the generator). Baking a message into the schema picks one and leaves the others wrong.

A rule whose generic wording is not good enough passes its own key, and that wins: `z.string().min(8, "validation.passwordTooShort")`.

**Nothing ever fails loudly.** An issue the map does not recognise falls back rather than emitting a key with no copy, and there are two fallbacks because Zod classifies on two axes:

| Situation                                                                    | Falls back to              |
| ---------------------------------------------------------------------------- | -------------------------- |
| An issue `code` with no `case` (`invalid_union`, `custom`)                   | `validation.invalid`       |
| `invalid_format` with a `format` not in `KNOWN_FORMATS` (`jwt`, `base64`, …) | `validation.invalidFormat` |

`code` and `format` are separate: `z.email()`, `z.uuid()` and `z.ipv4()` all report `invalid_format` and differ only in `issue.format`, which is why formats are matched by a `Set` inside that one case rather than by their own `case` arms.

**Adding a validation message** means editing two lists plus the copy, and the compiler enforces the last step:

1. `VALIDATION_KEYS` in `error-map.ts` - declares that the key exists
2. `KNOWN_FORMATS`, **only if** the key is a Zod format name - this is what allows the format to emit its own key instead of the generic one
3. `messages/en/validation.ts` **and** `messages/pt/validation.ts` - `Record<ValidationKey, string>` will not compile until both are there

Step 2 is the one that is easy to miss: adding `jwt` to `VALIDATION_KEYS` and the copy files without adding it to `KNOWN_FORMATS` leaves `z.jwt()` still resolving to `validation.invalidFormat`, with no error anywhere to say so.

**Import `z` from here, not from `zod`.** A consumer building its own schema - a form extending one of core's - takes zod through this package:

```ts
import { SignInSchema, z } from '@ordre/core/schemas';
```

Two copies of zod are two module instances, and the error map is installed on one of them. The second would emit English sentences where the first emits keys - identical types, no compiler complaint, and the only symptom is untranslated text in a UI. One import specifier makes that impossible.

`apps/api` is the exception and keeps its own `zod`, because `@asteasolutions/zod-to-openapi` requires it as a peer. Versions stay aligned by `syncpack`, which runs in CI.

The keys and their copy are listed on the [Error Codes](/internal-docs/reference/error-codes) page. How a form consumes them is in [`@ordre/ui`](#ordreui).

#### Messages

Every translated string in the product. App-specific copy still lives in each app's `shared/i18n/` and is merged with these at runtime - see [i18n Structure](#-i18n-structure).

```
packages/core/src/messages/
├── app.ts                # Locale-agnostic constants (name, domains)
├── en/
│   ├── errors.ts         # Record<ErrorCode, string>     - copy per catalog code
│   ├── validation.ts     # Record<ValidationKey, string> - copy per Zod issue key
│   └── index.ts          # Named namespaces + a default bundle
├── pt/                   # Same files, same keys
└── index.ts              # Re-exports { app, en, pt }
```

**What belongs here:** anything that names a concept rather than a screen - error copy, validation copy, shared product words. A page's own headline stays in that app's `shared/i18n/`.

**Why in core rather than its own package:** the copy for an error is keyed by the same `ErrorCode` the catalog defines. Split across packages, that means either duplicating strings or resolving them across a boundary `errorResponse` cannot cross, since it lives inside core. One package, one vocabulary.

**Coverage is enforced by the compiler.** `errors` is typed `Record<ErrorCode, string>` and `validation` is typed `Record<ValidationKey, string>`. Add a code or a key and core stops compiling until every locale has words for it.

**Per-locale exports matter.** `errorResponse` imports only `messages/en`, because the wire message is always English; nothing that ships the API pulls in Portuguese to do it. Apps import the barrel and pick a locale at runtime.

```ts
import { app, en, pt } from '@ordre/core/messages';
import { errors } from '@ordre/core/messages/en';

// one locale, on its own

// In an app, keys are absolute across namespaces:
t('errors.INVALID_EMAIL_OR_PASSWORD');
t('validation.email');
```

#### Routes

`API_ROUTES` holds every path the API serves, absolute and version-free, in `:param` form. It lives here rather than in `apps/api` because three consumers need three spellings of the same path, and no layer inside the API may import from another - the OpenAPI registrations sit in `controllers/` and the routers in `adapters/express/`, so neither can own the shared table.

| Consumer                                      | Spelling           | How                               |
| --------------------------------------------- | ------------------ | --------------------------------- |
| Express router (`adapters/express/routes/`)   | `/workspace/:id`   | `API_ROUTES.workspace.byId` as-is |
| OpenAPI document (`controllers/*.openapi.ts`) | `/workspace/{id}`  | `toOpenApiPath(...)`              |
| HTTP client (`@ordre/services`)               | `/workspace/8f0e…` | `buildPath(..., { id })`          |

`API_BASE_PATH` (`/v1`) is joined on at the two edges that own it - the Express mount in `server.ts` and the `servers` list in the OpenAPI document - so the table itself never carries a version.

`DASHBOARD_ROUTES` and `MARKETING_ROUTES` are the other half: the pages each frontend serves, spelled once so the API can link to them from an email.

#### Permissions

The role/permission matrix and `can()`. Documented in full under **[Authorization](/internal-docs/engineering/authorization)**.

### `@ordre/services`

**Purpose:** HTTP client layer the frontend apps use to call the API, so a component never builds a URL or handles a `fetch` directly.

**Tech stack:** native `fetch`, no client library. The transport is one small module; what would have been a library's job - typing, error shape, paths - is already owned by `@ordre/core`.

**Contains:**

- `createHttpClient` - the only module that touches `fetch`
- One service per domain (`auth`, and more as they land), each a thin map from method name to endpoint

**The factory, not a singleton.** The package never reads an environment variable: `createServices({ baseUrl })` takes the API origin and each app calls it once, in a single module, which every component then imports.

```ts
// apps/dashboard/src/shared/services.ts
export const services = createServices({ baseUrl: process.env.NEXT_PUBLIC_API_URL });
```

The alternative - the package reading `process.env` itself - cannot work: the Next apps expose `NEXT_PUBLIC_*` while the board is Vite, and `process.env` in a browser bundle breaks the board outright.

**What the client owns:** joining `API_BASE_PATH` and the origin, `credentials: 'include'` (the session is a cross-origin cookie, and without it every later call is unauthenticated), a JSON content type, and turning any failure - a `403`, an unparseable body, a dropped connection - into a `ServiceError` carrying a catalog `code`.

**Key constraint:** never imported by `apps/api` - the API is the thing it calls. Requests and responses are typed with `@ordre/core/schemas` and addressed with `API_ROUTES` from `@ordre/core/constants`, so both halves of the contract are shared rather than restated. `ServiceError` lives in `@ordre/core` rather than here, so the code that _reads_ it - the form layer in `@ordre/ui`, the error copy beside the catalog - never has to import a transport.

### `@ordre/db`

**Purpose:** Database schema, migrations, and connection. The single source of truth for how data is stored.

**Tech stack:** Drizzle ORM + drizzle-kit over node-postgres (`pg`). The `pg` driver rather than Neon's HTTP driver, because the API is a long-lived process - see [Infrastructure](/internal-docs/engineering/infrastructure).

**Contains:**

- Drizzle table definitions
- Database connection - a node-postgres (`pg`) connection pool wrapped by Drizzle
- Migrations (generated by drizzle-kit)
- Database scripts (generate, migrate, studio, push)

**Structure:**

```
packages/db/
├── src/
│   ├── schemas/
│   │   ├── better-auth.ts  # generated by Better Auth - do not hand-edit
│   │   ├── auth.ts         # hand-owned relations for the generated auth tables
│   │   ├── workspace.ts
│   │   ├── billing.ts
│   │   ├── outbox.ts
│   │   └── index.ts        # re-exports all tables (@ordre/db/schemas)
│   ├── migrations/         # generated by drizzle-kit
│   └── connection.ts       # pg pool + Drizzle factories (@ordre/db/connection)
├── drizzle.config.ts
└── package.json
```

**Export paths:**

| Path                   | Contents                                                                                                                                                         |
| ---------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `@ordre/db/connection` | `createPool(url)` (a node-postgres `pg.Pool`) + `createDb(pool)` (wraps a pool in Drizzle). The API composes these into one shared pool/`db` it owns - see below |
| `@ordre/db/schemas`    | Drizzle table definitions and relations (the schema namespace)                                                                                                   |

**Key constraint:** Only imported by `apps/api`. Never imported by frontend apps or `@ordre/core`.

### `@ordre/monitoring`

**Purpose:** Centralised observability - structured logging today, error tracking (Sentry) later. One place to configure _how_ every app logs, so output stays consistent across services and the backing platform can change without touching app code.

**Tech stack:** pino, with pino-http for Express access logs and pino-pretty in development only.

**Contains:**

- `createLogger(service?)` - a configured pino logger factory; the `console.log` replacement
- `httpLogger(service)` - a pino-http request logger factory for Express access logs
- Shared base config: log level, secret redaction (`authorization`, `cookie`, `*.password`, `*.token`), and dev-only pretty-printing

**Export paths:**

| Path                       | Contents                                                                                    |
| -------------------------- | ------------------------------------------------------------------------------------------- |
| `@ordre/monitoring/server` | `createLogger`, `httpLogger`, and the `Logger` type (Node runtimes: API + Next.js server)   |
| `@ordre/monitoring/client` | Browser logging / error tracking - empty stub for now, wired when the frontend apps need it |

**Design principle:** A thin composition layer, _not_ a provider abstraction. It exports configured instances - consumers call pino's real API through them - rather than wrapping them behind a generic interface. Adding or swapping a platform (e.g. shipping to Better Stack, or adding Sentry) is a change _inside this package_, not across every app.

**Usage:** Each app creates exactly one shared instance in its `config/` (calling `createLogger` again spins up a separate pino instance) and derives child loggers for per-module context:

```ts
// apps/api/src/config/logger.ts
import { createLogger } from "@ordre/monitoring/server";

export const logger = createLogger("api");

// elsewhere - object first, message second (keeps fields queryable)
import { logger } from "#/config/logger.ts";

logger.info({ userId }, "user logged in");
const log = logger.child({ controller: "auth" }); // stamps controller: "auth" on every line
```

**Production note:** `pino-pretty` is a devDependency and only loads in development. Production emits raw JSON - faster, and the format log platforms ingest.

**Key constraint:** The `./server` entry is for Node runtimes only (API, Next.js server code). Browser code uses `./client`, keeping Node-only pino transports out of frontend bundles.

### `@ordre/ui`

**Purpose:** Design system - atomic components, design tokens, and shared styles.

**Tech stack:** React 19, Tailwind CSS v4, `class-variance-authority` for variants, `lucide-react` for icons. Tested with Vitest + Testing Library in a real browser via Playwright.

**Contains:**

- Atomic components (`Button`, `TextField`, `Card`, etc.)
- Design tokens as CSS custom properties
- Shared global styles
- The shared form mechanism (`@ordre/ui/form`) - validation, error mapping, field binding

**Structure:**

```
packages/ui/
├── src/
│   ├── components/
│   │   ├── Button/
│   │   │   ├── Button.tsx
│   │   │   ├── Button.test.tsx
│   │   │   └── Button.stories.tsx
│   │   ├── Form/             # The one directory that is not one component
│   │   │   ├── TextField.tsx     # …plus TextArea, Checkbox, RadioGroup, Toggle, …
│   │   │   ├── Field.tsx         # The label/box/message anatomy they compose
│   │   │   ├── fieldVariants.ts  # The cva they share
│   │   │   └── useFieldControl.ts
│   │   └── index.ts          # Re-exports all components, grouped
│   ├── config/
│   │   └── postcss.ts        # Shared PostCSS config for consuming apps
│   ├── fonts/                # Self-hosted font files (Geist, Geist Mono, Plus Jakarta Sans)
│   ├── helpers/              # Small styling helpers
│   ├── form/                 # The shared form mechanism (@ordre/ui/form)
│   │   ├── useAppForm.ts     # Schema and handler in, bound fields + onSubmit out
│   │   ├── applyServiceError.ts  # A failed request onto the form
│   │   └── translate.ts      # The injected `t`, see below
│   ├── hooks/                # Shared React hooks
│   ├── icons/
│   │   ├── Icons.tsx         # Re-exports Lucide icon set + custom icons
│   │   ├── Iconography.mdx   # Storybook docs for the icon system
│   │   └── custom/
│   │       └── Logo.tsx
│   └── styles/
│       ├── main.css          # Entry point (imports fonts.css + tailwind.css + @source)
│       ├── tailwind.css      # Imports every token file
│       ├── fonts.css         # @font-face declarations
│       └── tokens/           # One .css per group, each with a sibling .mdx for Storybook
│           ├── colors.css    # …plus typography, spacing, radius, shadows,
│           └── colors.mdx    #    motion, breakpoint, container
└── package.json
```

**Component layout:** one directory per component, holding its `.tsx`, `.test.tsx`, and
`.stories.tsx`. `Form/` is the deliberate exception: its controls sit flat beside the
field anatomy, cva, and hooks they all compose, because nesting each in its own
directory would leave every one of them importing its siblings from a parent.

**The form mechanism** (`src/form/`, distinct from `src/components/Form/`, which is the
controls) is here rather than in `@ordre/core` for one reason: it is React, and core's
whole value is having none. Every app validates the same way, so the decisions are made
once - `onTouched` then `onChange`, messages resolved from keys, `details` onto fields and
everything else into the banner. The handler goes in as an option rather than being
wrapped at the call site, so no view can hand a `form` a submit that has not been
through the error mapping.

```tsx
const { field, onSubmit, rootError, isBusy } = useAppForm({ schema, t, onSubmit: send });

<TextField {...field('email')} label={t('Login.email.label')} />;
```

**Why `t` is a parameter and not a hook call.** The apps do not share an i18n runtime -
the Next apps use `next-intl`, the board uses `i18next`. A shared layer that called either
one directly could serve two of the three apps. Injecting the resolved function costs one
line at each call site and keeps the mechanism portable.

**Component groups:** the headings in `components/index.ts` - Primitives, Form,
Surfaces, Shell - are also the Storybook sidebar folders. Adding a component to the
barrel and filing it in Storybook is one decision, not two.

**Usage in apps:**

```ts
import { Button } from '@ordre/ui/components';
import '@ordre/ui/styles/main';

// imported once in root layout
```

**Package exports:** `./components`, `./config/postcss`, `./styles/*`, `./fonts/*`, `./icons`, `./helpers/*`, `./hooks/*`.

**Storybook requirement:** Every component in `@ordre/ui` must ship with a co-located `.stories.tsx`. Stories are published as part of the deployed Storybook at `storybook.ordre.app` - adding a component without a story is a review blocker.

**Tailwind v4 note:** No `tailwind.config.ts`. Tokens are CSS custom properties consumed directly via Tailwind's `@source` directive.

**Constraints.** Three rules keep this package importable by every consumer:

- **No Next.js, React Router, or app-level code.** It must work in any React app.
- **Atomic components only.** Feature-level compositions belong to the app that needs them.
- **No business logic.** A component here knows about props and styles, never about Ordre's domain.

### `@ordre/config`

**Purpose:** Shared tooling configurations - ESLint and TypeScript presets.

**Tech stack:** ESLint 9, TypeScript, and Prettier (with `@trivago/prettier-plugin-sort-imports`) - presets only, no runtime code.

**Structure:**

```
packages/config/
├── eslint/
│   ├── base.ts                 # Shared base config (TS, turbo, prettier)
│   ├── next.ts                 # Next.js preset (marketing, dashboard)
│   └── react.ts                # React / React Router preset (board, ui)
├── typescript/
│   ├── base.json
│   ├── nextjs.json             # Preset for Next.js apps
│   ├── react-library.json      # Preset for React libraries (e.g. @ordre/ui)
```

### 🛰️ api

**Tech stack:** Express 5 on Node.js, Better Auth for sessions, Drizzle ORM via `@ordre/db`, Zod 4 via `@ordre/core/schemas`, Resend for email, `helmet` + `cors` for HTTP hardening, `@asteasolutions/zod-to-openapi` for the spec, and `supertest` for route tests.

The API app is an Express (Node.js) server - deployed as a standard long-running process in both development and production. Routes are thin HTTP adapters that call controllers; controllers contain the business logic, the OpenAPI contract, and their tests, and import from `@ordre/core/schemas` for validation and `@ordre/db` for database queries. See [Infrastructure](/internal-docs/engineering/infrastructure) for compute migration options.

**URL shape:** everything is served under `API_BASE_PATH` (`/v1`) on the API's own subdomain - `https://api.ordre.app/v1/workspace`. The prefix buys versioning rather than namespacing (the subdomain already does that), and it doubles as the scanner gate in `server.ts`, which answers anything outside it with an empty 404 before helmet, CORS, and the access log run. The paths below it come from `API_ROUTES` in [`@ordre/core/constants`](#ordrecore), never from string literals in a router.

**Database connection ownership:** `@ordre/db/connection` exposes the `createPool` / `createDb` factories, but the API app owns the live connection. `config/db.ts` creates exactly one `pg` pool (and its Drizzle `db`) per process and exports both; controllers and `config/auth.ts` import that shared `db`. Because the server is long-lived, the entrypoint (`adapters/express/index.ts`) drains the pool on `SIGTERM`/`SIGINT` so deploys and `node --watch` reloads finish in-flight queries before exiting.

```
apps/api/src/
├── adapters/
│   └── express/
│       ├── middlewares/                # authenticate, rlsContext, workspace access/quota
│       ├── routes/
│       │   ├── boards/
│       │   │   ├── boards.routes.ts    # thin: parses req, calls controller, sends res
│       │   │   └── boards.routes.test.ts   # integration tests (real DB)
│       │   └── members/
│       │       └── members.routes.ts
│       ├── server.ts                   # Express app assembly (helmet, CORS, routes)
│       └── index.ts                    # entrypoint: listen, start worker, graceful shutdown
│
├── config/                             # env, logger, db pool, RLS context, auth, OpenAPI, urls
│
├── controllers/                        # business logic + OpenAPI contract + tests
│   ├── boards/
│   │   ├── index.ts                    # barrel - public surface only
│   │   ├── get-boards.controller.ts
│   │   ├── create-board.controller.ts
│   │   ├── boards.schemas.ts           # local Zod schemas (optional)
│   │   ├── boards.openapi.ts           # OpenAPI registration for the feature
│   │   ├── get-boards.test.ts
│   │   └── helpers/                    # internal helpers (only when >1 file)
│   └── members/
│       └── ...
│
├── services/                           # third-party providers (email/Resend)
├── workers/                            # background loops (outbox delivery)
├── utils/                              # framework-agnostic helpers
├── types/                              # request context + DB row types
└── test/                               # harness: fixtures, seed/reset, owner DB
```

Two folders sit outside the request path and are worth calling out:

| Folder      | Contents                                                                                                                                                                    |
| ----------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `services/` | Integrations with a third party. One module per provider, throwing on failure so the caller decides what to do about it.                                                    |
| `workers/`  | Long-running background loops owned by the process. Started from `adapters/express/index.ts` - never from `server.ts`, so importing the app in a test doesn't start a loop. |

The [outbox worker](/internal-docs/engineering/outbox) is the current example of both: producers queue a row inside the request transaction, and the worker delivers it through `services/email.ts` afterwards.

#### Controller folder convention

Every controller folder is a self-contained feature unit that owns the business logic, OpenAPI contract, tests, and internal helpers. Co-locating the OpenAPI registration with the controller (instead of with the Express route) keeps the contract independent of the HTTP adapter - swapping Express for Lambda or Vercel Functions only touches `adapters/`.

| File              | Responsibility                                                                                                                    |
| ----------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| `index.ts`        | Barrel. Re-exports public surface only (`*.controller.ts` and `*.openapi.ts`). Helpers and local types stay private.              |
| `*.controller.ts` | Controller function(s). No Express dependency. Imports from `@ordre/core/schemas` and `@ordre/db`.                                |
| `*.openapi.ts`    | OpenAPI registration for the feature. One per folder, not one per controller.                                                     |
| `*.schemas.ts`    | Local Zod schemas. Use only when controller-internal; otherwise put the schema in `@ordre/core/schemas`.                          |
| `*.test.ts`       | Co-located unit tests for fault injection (mocked DB). Full-path coverage lives in `*.routes.test.ts` - see [Testing](./testing). |
| `helpers/`        | Folder for 2+ internal helpers. For a single helper, use a flat `*.helpers.ts` file instead.                                      |

**Naming:** `<feature>.<role>.ts` (e.g. `get-boards.controller.ts`, `boards.openapi.ts`). The `.controller.ts` suffix disambiguates controllers from helpers and schemas as the folder grows.

#### Subpath imports

The API uses Node's `imports` field to expose each controller folder as a single import surface, so consumers never reach past `index.ts`:

```jsonc
// apps/api/package.json
{
  "imports": {
    "#env": "./src/config/env.ts",
    "#controllers/*": "./src/controllers/*/index.ts",
    "#/*": "./src/*",
  },
}
```

```ts
// adapters/express/routes/boards/boards.routes.ts
import { boardsOpenApi, createBoard, getBoards } from '#controllers/boards';
```

#### Responsibility split

Routes only know about HTTP - they parse the request and send the response. Controllers contain the logic - they import from `@ordre/core/schemas` and `@ordre/db`, and have no Express dependency.

```ts
// routes/boards/boards.routes.ts - only knows about HTTP
import { createBoard } from "#controllers/boards";

router.post("/boards", async (req, res) => {
  const result = await createBoard(req.body, req.user.workspaceId);
  res.json(result);
});

// controllers/boards/create-board.controller.ts - only knows about logic
import { createBoardSchema } from "@ordre/core/schemas";
import { boards } from "@ordre/db/schemas";

import { db } from "#/config/db.ts"; // the app's shared pg pool + Drizzle

export async function createBoard(body: unknown, workspaceId: string) {
  const data = createBoardSchema.parse(body);
  const [row] = await db
    .insert(boards)
    .values({ ...data, workspaceId })
    .returning();
  return row;
}
```

#### API documentation

Each controller folder includes a `.openapi.ts` file that registers the feature's routes against the same `@ordre/core/schemas` schemas used by the controller. The top-level `openapi.ts` imports from each `#controllers/*` and generates an `openapi.json` spec consumed by the `apps/docs` API reference. See [Documentation - Fumadocs](/internal-docs/engineering/infrastructure) for the docs app details.

#### If the compute layer changes

If migrating to Lambda or Vercel Functions, each route becomes a new adapter file that calls the same controller. Controllers and their `.openapi.ts` files have no Express dependency, so nothing in `controllers/`, `@ordre/core`, or `@ordre/db` changes.

### 📚 docs

**Tech stack:** Next.js 16 + Fumadocs (`fumadocs-core`, `fumadocs-ui`, `fumadocs-mdx`), with `fumadocs-openapi` generating the API reference and `lucide-react` for page icons.

The API is documented at `docs.ordre.app/api-docs`, inside the same Fumadocs app that serves the internal guides. The OpenAPI spec is generated at build time from route registrations in `apps/api`, not maintained manually.

**How it works:**

1. Each controller folder includes a `.openapi.ts` file that registers the feature's request and response shapes against the same `@ordre/core/schemas` Zod schemas used by the controller
2. The `@asteasolutions/zod-to-openapi` library converts those Zod schemas into OpenAPI 3.x definitions - no schema duplication
3. The top-level `openapi.ts` entry point combines all `.openapi.ts` files and generates a single `openapi.json` spec
4. `fumadocs-openapi` turns that spec into MDX pages (one per operation) rendered with the Fumadocs UI, including an interactive request playground

**App structure:**

```
apps/docs/
├── public/
│   └── openapi.json          # Generated at build time from apps/api
├── content/
│   ├── docs/                 # Internal guides (/internal-docs)
│   └── api-docs/             # Generated from openapi.json (/api-docs)
├── src/                      # Next.js + Fumadocs app
└── package.json
```

**Adding a guide page:** create the MDX file under `content/docs` with `title`,
`icon`, and `description` frontmatter, then add its path to the `meta.json` that
controls its section. A page missing from `meta.json` renders but is not linked
from the sidebar. The path maps straight to the URL: `content/docs/<path>.mdx` is
served at `/internal-docs/<path>`, and `index.mdx` at `/internal-docs`.

Two pages are **generated, never written by hand**, and carry a banner saying so:

| Page                        | Generated from             | Command             |
| --------------------------- | -------------------------- | ------------------- |
| `reference/error-codes.mdx` | `packages/core/src/errors` | `pnpm docs:errors`  |
| `content/api-docs/**`       | `public/openapi.json`      | `pnpm docs:openapi` |

`content/api-docs` is gitignored and rebuilt on `postinstall`, `build`, and
`check-types`. `public/openapi.json` is regenerated by lint-staged whenever
anything under `apps/api` changes.

**Hosting:** Deployed to `docs.ordre.app` via Vercel, protected by Vercel's built-in password protection during development and beta.

**Alternatives considered:** Scalar (polished standalone UI, but a separate look from the guides), Swagger UI (dated look and feel), Redoc (read-only, no API client).

## 🗂️ Three-Folder Convention

Each folder inside `src/` has a single, non-overlapping responsibility.

| Folder    | Responsibility                                                                                                                                                                                                |
| --------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `app/`    | Route definitions, layouts, and framework-level concerns (middleware, entry files, API routes). Re-exports views. No business logic. All apps use `app/` - the Board app nests routes under `app/pages/`.     |
| `views/`  | Page UI components, page-level logic, tests, and Storybook stories. A view with any logic splits into `ui/` (JSX) and `model/` (hooks, form schemas), so a screen's behaviour can be read without its markup. |
| `shared/` | Cross-cutting code reused across multiple views: hooks, utils, types, i18n.                                                                                                                                   |

**Flow example (Board app):**

```tsx
// 1. Route module - src/app/pages/home/home.tsx
import { HomePage } from '@/views/Home';
export default function Home() { return <HomePage />; }

// 2. View - src/views/Home/ui/HomePage.tsx
import { Button } from '@ordre/ui';

export function HomePage() { ... }

// 3. Test - src/views/BoardView/ui/BoardView.test.tsx
test('renders board timeline', () => { ... });
```

## 🌍 i18n Structure

**Initial languages:** English (`en`) and Portuguese (`pt`).

**Shared strings** (app constants, status labels, error and validation copy, common UI words) live in [`@ordre/core/messages`](#messages) and are merged with app-specific strings at runtime. This section covers how each app _consumes_ them; what they contain and why they live in core is documented there.

**Libraries per app:**

| App       | Library                                       | Locale detection                                               | URL prefix                                     |
| --------- | --------------------------------------------- | -------------------------------------------------------------- | ---------------------------------------------- |
| Marketing | `next-intl`                                   | Path-based via `next-intl` routing                             | `as-needed` - `en` no prefix, `pt` → `/br`     |
| Dashboard | `next-intl`                                   | Accept-Language header via `Negotiator` + `intl-localematcher` | None                                           |
| Board     | `i18next` + `react-i18next` + `remix-i18next` | Order: custom path (`/br` → `pt`) → `lng` cookie → header      | `en` no prefix, `pt` → `/br` (via app helpers) |

### Marketing (`next-intl`)

```
src/shared/i18n/
├── routing.ts                 # defineRouting({ locales: ['en','pt'], defaultLocale: 'en', localePrefix: { mode:'as-needed', prefixes:{ pt:'/br' } } })
├── navigation.ts              # createNavigation(routing) - exports Link, redirect, usePathname, useRouter, getPathname
├── requests.ts                # getRequestConfig - spreads @ordre/core `app` + global `en|pt` + local messages
└── messages/
    ├── en.ts
    └── pt.ts
```

### Dashboard (`next-intl`)

```
src/shared/i18n/
├── requests.ts                # getRequestConfig - matches Accept-Language via Negotiator + intl-localematcher
└── messages/
    ├── en.ts
    └── pt.ts
```

### Board (`i18next` + `remix-i18next`)

```
src/
├── shared/i18n/
│   ├── index.ts                 # Resource map: { en: { translation: en }, pt: { translation: pt } }
│   └── messages/
│       ├── en.ts                # Spreads @ordre/core `app` + global `en` + app-specific strings
│       └── pt.ts
│
└── app/
    ├── locale/locales.ts        # supportedLanguages, fallbackLanguage, localePrefixes ({ en:'', pt:'/br' }), getLocaleFromPath, stripLocalePrefix
    ├── middleware/i18next.ts    # createI18nextMiddleware - lng cookie, detection order ['custom','cookie','header'], i18next module augmentation for typed resources
    └── api/locales.ts           # /api/locales/:lng/:ns - serves namespace resources (used by i18next-fetch-backend on the client)
```
