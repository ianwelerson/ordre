## 📁 Monorepo Root

```
ordre/
├── apps/                     # Runnable applications
│   ├── api/                  # Backend API (Express)
│   ├── dashboard/            # Dashboard Next.js app (workspace members)
│   ├── marketing/            # Marketing Next.js app
│   ├── portal/               # [FUTURE] Client portal Next.js app
│   ├── board/                # Board (shareable board) React app
│   ├── docs/                 # Guides + generated API reference (Fumadocs)
│   └── storybook/            # Component documentation
│
├── packages/                 # Shared, reusable code
│   ├── core/                 # Zod schemas, TypeScript types & shared error catalog
│   ├── db/                   # Database schema, migrations & connection
│   ├── services/             # [PLANNED] HTTP client layer for frontend apps
│   ├── monitoring/           # Structured logging (pino) & future error tracking
│   ├── ui/                   # Design system & components
│   ├── i18n/                 # Shared translations
│   └── config/               # Shared tooling configs
│
├── turbo.json                # Turborepo pipeline config
├── pnpm-workspace.yaml       # Workspace definition
└── package.json              # Root dependencies
```

**Rule:** `apps/` = things that run. `packages/` = things that are shared.

## 🧰 Shared Tech Stack

Every workspace sits on the same base, so the per-workspace sections below list
only what is specific to them.

| Concern      | Choice                                                        |
| ------------ | ------------------------------------------------------------- |
| Language     | TypeScript, strict, via `@ordre/config/typescript/*`          |
| Monorepo     | Turborepo + pnpm workspaces                                   |
| Runtime      | Node.js 24+ (see `.nvmrc`)                                    |
| Testing      | Vitest, with `@vitest/coverage-v8`                            |
| Linting      | ESLint 9 flat config, via `@ordre/config/eslint/*`            |
| Formatting   | Prettier with import sorting, via `@ordre/config/prettier`    |
| Dependencies | Syncpack, keeping shared versions aligned (`pnpm packages:lint`) |
| Local HTTPS  | portless - see [Running the Project](/internal-docs/setup/running-the-project) |

Frontend workspaces add React 19, Tailwind CSS v4, and Testing Library with
Playwright as Vitest's browser provider.

<Callout>
  **Major versions only, on this page.** Exact versions live in each workspace's
  `package.json` and in `pnpm-lock.yaml` - a number copied into prose goes stale on
  the next dependency bump.
</Callout>

## 📦 Package Architecture

The packages follow a strict dependency flow. Upper layers may import from lower layers. **Lower layers must never import from upper layers**, and no package imports an app.

```
┌──────────────────────────────────────────────────────────┐
│                      Frontend Apps                       │
│              dashboard · board · marketing               │
└──────────────────────────┬───────────────────────────────┘
                           │
              ┌────────────┴────────────┐
              ▼                         ▼
┌─────────────────────┐   ┌────────────────────────────────┐
│      @ordre/ui      │   │          @ordre/i18n           │
│ Components & tokens │   │      Shared translations       │
└─────────────────────┘   └────────────────────────────────┘


┌──────────────────────────────────────────────────────────┐
│                         apps/api                         │
│    imports @ordre/db, @ordre/monitoring, @ordre/core     │
└──────────────────────────┬───────────────────────────────┘
                           │
              ┌────────────┴────────────┐
              ▼                         ▼
┌─────────────────────┐   ┌────────────────────────────────┐
│  @ordre/monitoring  │   │           @ordre/db            │
│     pino logging    │   │   Drizzle tables, migrations   │
└─────────────────────┘   │   Only imported by apps/api    │
                          └───────────────┬────────────────┘
                                          │
                                          ▼
┌──────────────────────────────────────────────────────────┐
│                       @ordre/core                        │
│             schemas · types · errors · enums             │
│                 constants · permissions                  │
│             The floor: no Drizzle, no React.             │
│     Imported directly by apps/api and apps/docs too.     │
└──────────────────────────────────────────────────────────┘

  @ordre/config  -  devDependency of every workspace that has its own
                    ESLint/TypeScript config; ships no runtime code
```

The edges above are the real ones today, not the intended end state:

| Workspace                            | Depends on                                          |
| ------------------------------------ | --------------------------------------------------- |
| `apps/api`                           | `@ordre/core`, `@ordre/db`, `@ordre/monitoring`     |
| `apps/dashboard` · `board` · `marketing` | `@ordre/ui`, `@ordre/i18n`                       |
| `apps/docs`                          | `@ordre/core` (the error-code page is generated from its catalog) |
| `apps/storybook`                     | `@ordre/ui`                                         |
| `@ordre/db`                          | `@ordre/core`                                       |
| `@ordre/core` · `ui` · `monitoring`  | nothing but `@ordre/config`                         |
| `@ordre/i18n` · `@ordre/config`      | nothing at all                                      |

`apps/storybook` and `@ordre/i18n` carry no `@ordre/config` because neither has an
ESLint or TypeScript config of its own - Storybook lints through the workspaces it
loads stories from, and `@ordre/i18n` is plain message objects.

Two rules fall out of that shape and are worth stating explicitly:

- **`@ordre/db` is imported by `apps/api` and nothing else.** No frontend, and not `@ordre/core`. Drizzle and `pg` stay out of every browser bundle.
- **`@ordre/core` is the floor.** It has no Drizzle and no React dependency, which is what lets both the API and the frontends import it.

<Callout>
  **The frontends do not import `@ordre/core` yet.** They will once they call the
  API and need its schemas and types - today they consume only `@ordre/ui` and
  `@ordre/i18n`. The constraint above ("importable by any app") describes what the
  package is built to allow, not a dependency that exists.
</Callout>

## 🔍 Package Responsibilities

### `@ordre/core`

**Purpose:** Shared API contract - Zod schemas, TypeScript types, and a shared error catalog consumed by both the API and frontend apps.

**Tech stack:** Zod 4 only. No Drizzle, no React - that is what keeps it importable by anything.

**Contains:**

- Zod validation schemas (request bodies, response shapes)
- TypeScript types inferred from those schemas via `z.infer<>`, plus shared type primitives (`ErrorDefinition`, `ErrorMap`, `StatusCodes`)
- A shared error catalog mapping stable error keys to a message and HTTP status

**Export paths:**

| Path                      | Contents                                                              |
| ------------------------- | --------------------------------------------------------------------- |
| `@ordre/core/schemas`     | Zod schemas for request and response validation                       |
| `@ordre/core/types`       | TypeScript types inferred from schemas                                |
| `@ordre/core/errors`      | Error catalog (`{ key: { message, status } }`)                        |
| `@ordre/core/enums`       | Canonical value lists, several of which back Postgres enums           |
| `@ordre/core/constants`   | Values identical in every environment - client route paths, TTLs      |
| `@ordre/core/permissions` | The role/permission matrix and `can()` - see [Authorization](/internal-docs/engineering/authorization) |

**Error catalog:** Errors are grouped by domain and keyed by a stable identifier, each resolving to an `ErrorDefinition` (`message` + optional `status`). The API maps these onto its responses - for example, `VALIDATION_ERRORS.INVALID_INPUT` drives the `400` returned when Better Auth rejects a request body.

```ts
import { VALIDATION_ERRORS } from "@ordre/core/errors";

VALIDATION_ERRORS.INVALID_INPUT; // { status: 400, message: "Validation error" }
```

**Key constraint:** No Drizzle dependency. No React dependency. Importable by any app - API, dashboard, board, or marketing.

**Tech stack:** undecided - the client library is chosen when the first service lands.

**Planned contents:**

**Key constraint:** never imported by `apps/api` - the API is the thing it calls. Requests and responses will be typed with `@ordre/core/schemas`, so the contract is shared rather than restated.

### `@ordre/db`

**Purpose:** Database schema, migrations, and connection. The single source of truth for how data is stored.

**Tech stack:** Drizzle ORM + drizzle-kit over node-postgres (`pg`). The `pg` driver rather than Neon's HTTP driver, because the API is a long-lived process - see [Infrastructure](/internal-docs/engineering/infrastructure).

**Contains:**

- Drizzle table definitions
- Database connection - a node-postgres (`pg`) connection pool wrapped by Drizzle
- Migrations (generated by drizzle-kit)
- Database scripts (generate, migrate, studio, push)

**Structure:**

```
packages/db/
├── src/
│   ├── schemas/
│   │   ├── better-auth.ts  # generated by Better Auth - do not hand-edit
│   │   ├── auth.ts         # hand-owned relations for the generated auth tables
│   │   ├── workspace.ts
│   │   ├── billing.ts
│   │   ├── outbox.ts
│   │   └── index.ts        # re-exports all tables (@ordre/db/schemas)
│   ├── migrations/         # generated by drizzle-kit
│   └── connection.ts       # pg pool + Drizzle factories (@ordre/db/connection)
├── drizzle.config.ts
└── package.json
```

**Export paths:**

| Path                   | Contents                                                              |
| ---------------------- | -------------------------------------------------------------------- |
| `@ordre/db/connection` | `createPool(url)` (a node-postgres `pg.Pool`) + `createDb(pool)` (wraps a pool in Drizzle). The API composes these into one shared pool/`db` it owns - see below |
| `@ordre/db/schemas`    | Drizzle table definitions and relations (the schema namespace)       |

**Key constraint:** Only imported by `apps/api`. Never imported by frontend apps or `@ordre/core`.

### `@ordre/monitoring`

**Purpose:** Centralised observability - structured logging today, error tracking (Sentry) later. One place to configure _how_ every app logs, so output stays consistent across services and the backing platform can change without touching app code.

**Tech stack:** pino, with pino-http for Express access logs and pino-pretty in development only.

**Contains:**

- `createLogger(service?)` - a configured pino logger factory; the `console.log` replacement
- `httpLogger(service)` - a pino-http request logger factory for Express access logs
- Shared base config: log level, secret redaction (`authorization`, `cookie`, `*.password`, `*.token`), and dev-only pretty-printing

**Export paths:**

| Path                       | Contents                                                                                    |
| -------------------------- | ------------------------------------------------------------------------------------------- |
| `@ordre/monitoring/server` | `createLogger`, `httpLogger`, and the `Logger` type (Node runtimes: API + Next.js server)   |
| `@ordre/monitoring/client` | Browser logging / error tracking - empty stub for now, wired when the frontend apps need it |

**Design principle:** A thin composition layer, _not_ a provider abstraction. It exports configured instances - consumers call pino's real API through them - rather than wrapping them behind a generic interface. Adding or swapping a platform (e.g. shipping to Better Stack, or adding Sentry) is a change _inside this package_, not across every app.

**Usage:** Each app creates exactly one shared instance in its `config/` (calling `createLogger` again spins up a separate pino instance) and derives child loggers for per-module context:

```ts
// apps/api/src/config/logger.ts
import { createLogger } from "@ordre/monitoring/server";

export const logger = createLogger("api");

// elsewhere - object first, message second (keeps fields queryable)
import { logger } from "#/config/logger.ts";

logger.info({ userId }, "user logged in");
const log = logger.child({ controller: "auth" }); // stamps controller: "auth" on every line
```

**Production note:** `pino-pretty` is a devDependency and only loads in development. Production emits raw JSON - faster, and the format log platforms ingest.

**Key constraint:** The `./server` entry is for Node runtimes only (API, Next.js server code). Browser code uses `./client`, keeping Node-only pino transports out of frontend bundles.

### `@ordre/ui`

**Purpose:** Design system - atomic components, design tokens, and shared styles.

**Tech stack:** React 19, Tailwind CSS v4, `class-variance-authority` for variants, `lucide-react` for icons. Tested with Vitest + Testing Library in a real browser via Playwright.

**Contains:**

- Atomic components (`Button`, `Input`, `Card`, etc.)
- Design tokens as CSS custom properties
- Shared global styles

**Structure:**

```
packages/ui/
├── src/
│   ├── components/
│   │   ├── Button/
│   │   │   ├── Button.tsx
│   │   │   ├── Button.test.tsx
│   │   │   └── Button.stories.tsx
│   │   └── index.ts          # Re-exports all components
│   ├── config/
│   │   └── postcss.ts        # Shared PostCSS config for consuming apps
│   ├── fonts/                # Self-hosted font files (Geist, Geist Mono, Plus Jakarta Sans)
│   ├── icons/
│   │   ├── Icons.tsx         # Re-exports Lucide icon set + custom icons
│   │   ├── Iconography.mdx   # Storybook docs for the icon system
│   │   └── custom/
│   │       └── Logo.tsx
│   └── styles/
│       ├── main.css          # Entry point (imports fonts.css + tailwind.css + @source)
│       ├── tailwind.css      # Tailwind base + tokens (design tokens as CSS custom properties)
│       ├── fonts.css         # @font-face declarations
│       └── colors.mdx        # Storybook docs for the color palette
└── package.json
```

**Usage in apps:**

```ts
import { Button } from "@ordre/ui/components";
import "@ordre/ui/styles/main"; // imported once in root layout
```

**Package exports:** `./components`, `./config/postcss`, `./styles/*`, `./fonts/*`, `./icons`, `./helpers/*`.

**Storybook requirement:** Every component in `@ordre/ui` must ship with a co-located `.stories.tsx`. Stories are published as part of the deployed Storybook at `storybook.ordre.app` - adding a component without a story is a review blocker.

**Tailwind v4 note:** No `tailwind.config.ts`. Tokens are CSS custom properties consumed directly via Tailwind's `@source` directive.

### 🛰️ api

**Tech stack:** Express 5 on Node.js, Better Auth for sessions, Drizzle ORM via `@ordre/db`, Zod 4 via `@ordre/core/schemas`, Resend for email, `helmet` + `cors` for HTTP hardening, `@asteasolutions/zod-to-openapi` for the spec, and `supertest` for route tests.

The API app is an Express (Node.js) server - deployed as a standard long-running process in both development and production. Routes are thin HTTP adapters that call controllers; controllers contain the business logic, the OpenAPI contract, and their tests, and import from `@ordre/core/schemas` for validation and `@ordre/db` for database queries. See [Infrastructure](/internal-docs/engineering/infrastructure) for compute migration options.

**Database connection ownership:** `@ordre/db/connection` exposes the `createPool` / `createDb` factories, but the API app owns the live connection. `config/db.ts` creates exactly one `pg` pool (and its Drizzle `db`) per process and exports both; controllers and `config/auth.ts` import that shared `db`. Because the server is long-lived, the entrypoint (`adapters/express/index.ts`) drains the pool on `SIGTERM`/`SIGINT` so deploys and `node --watch` reloads finish in-flight queries before exiting.

```
apps/api/src/
├── adapters/
│   └── express/
│       ├── middlewares/                # authenticate, rlsContext, workspace access/quota
│       ├── routes/
│       │   ├── boards/
│       │   │   ├── boards.routes.ts    # thin: parses req, calls controller, sends res
│       │   │   └── boards.routes.test.ts   # integration tests (real DB)
│       │   └── members/
│       │       └── members.routes.ts
│       ├── server.ts                   # Express app assembly (helmet, CORS, routes)
│       └── index.ts                    # entrypoint: listen, start worker, graceful shutdown
│
├── config/                             # env, logger, db pool, RLS context, auth, OpenAPI, urls
│
├── controllers/                        # business logic + OpenAPI contract + tests
│   ├── boards/
│   │   ├── index.ts                    # barrel - public surface only
│   │   ├── get-boards.controller.ts
│   │   ├── create-board.controller.ts
│   │   ├── boards.schemas.ts           # local Zod schemas (optional)
│   │   ├── boards.openapi.ts           # OpenAPI registration for the feature
│   │   ├── get-boards.test.ts
│   │   └── helpers/                    # internal helpers (only when >1 file)
│   └── members/
│       └── ...
│
├── services/                           # third-party providers (email/Resend)
├── workers/                            # background loops (outbox delivery)
├── utils/                              # framework-agnostic helpers
├── types/                              # request context + DB row types
└── test/                               # harness: fixtures, seed/reset, owner DB
```

Two folders sit outside the request path and are worth calling out:

| Folder      | Contents                                                                                     |
| ----------- | -------------------------------------------------------------------------------------------- |
| `services/` | Integrations with a third party. One module per provider, throwing on failure so the caller decides what to do about it. |
| `workers/`  | Long-running background loops owned by the process. Started from `adapters/express/index.ts` - never from `server.ts`, so importing the app in a test doesn't start a loop. |

The [outbox worker](/internal-docs/engineering/outbox) is the current example of both: producers queue a row inside the request transaction, and the worker delivers it through `services/email.ts` afterwards.

#### Controller folder convention

Every controller folder is a self-contained feature unit that owns the business logic, OpenAPI contract, tests, and internal helpers. Co-locating the OpenAPI registration with the controller (instead of with the Express route) keeps the contract independent of the HTTP adapter - swapping Express for Lambda or Vercel Functions only touches `adapters/`.

| File              | Responsibility                                                                                                       |
| ----------------- | -------------------------------------------------------------------------------------------------------------------- |
| `index.ts`        | Barrel. Re-exports public surface only (`*.controller.ts` and `*.openapi.ts`). Helpers and local types stay private. |
| `*.controller.ts` | Controller function(s). No Express dependency. Imports from `@ordre/core/schemas` and `@ordre/db`.                   |
| `*.openapi.ts`    | OpenAPI registration for the feature. One per folder, not one per controller.                                        |
| `*.schemas.ts`    | Local Zod schemas. Use only when controller-internal; otherwise put the schema in `@ordre/core/schemas`.             |
| `*.test.ts`       | Co-located unit tests for fault injection (mocked DB). Full-path coverage lives in `*.routes.test.ts` - see [Testing](./testing). |
| `helpers/`        | Folder for 2+ internal helpers. For a single helper, use a flat `*.helpers.ts` file instead.                         |

**Naming:** `<feature>.<role>.ts` (e.g. `get-boards.controller.ts`, `boards.openapi.ts`). The `.controller.ts` suffix disambiguates controllers from helpers and schemas as the folder grows.

#### Subpath imports

The API uses Node's `imports` field to expose each controller folder as a single import surface, so consumers never reach past `index.ts`:

```jsonc
// apps/api/package.json
{
  "imports": {
    "#env": "./src/config/env.ts",
    "#controllers/*": "./src/controllers/*/index.ts",
    "#/*": "./src/*",
  },
}
```

```ts
// adapters/express/routes/boards/boards.routes.ts
import { getBoards, createBoard, boardsOpenApi } from "#controllers/boards";
```

#### Responsibility split

Routes only know about HTTP - they parse the request and send the response. Controllers contain the logic - they import from `@ordre/core/schemas` and `@ordre/db`, and have no Express dependency.

```ts
// routes/boards/boards.routes.ts - only knows about HTTP
import { createBoard } from "#controllers/boards";

router.post("/boards", async (req, res) => {
  const result = await createBoard(req.body, req.user.workspaceId);
  res.json(result);
});

// controllers/boards/create-board.controller.ts - only knows about logic
import { createBoardSchema } from "@ordre/core/schemas";
import { boards } from "@ordre/db/schemas";

import { db } from "#/config/db.ts"; // the app's shared pg pool + Drizzle

export async function createBoard(body: unknown, workspaceId: string) {
  const data = createBoardSchema.parse(body);
  const [row] = await db
    .insert(boards)
    .values({ ...data, workspaceId })
    .returning();
  return row;
}
```

#### API documentation

Each controller folder includes a `.openapi.ts` file that registers the feature's routes against the same `@ordre/core/schemas` schemas used by the controller. The top-level `openapi.ts` imports from each `#controllers/*` and generates an `openapi.json` spec consumed by the `apps/docs` API reference. See [Documentation - Fumadocs](/internal-docs/engineering/infrastructure) for the docs app details.

#### If the compute layer changes

If migrating to Lambda or Vercel Functions, each route becomes a new adapter file that calls the same controller. Controllers and their `.openapi.ts` files have no Express dependency, so nothing in `controllers/`, `@ordre/core`, or `@ordre/db` changes.

### 📚 docs

**Tech stack:** Next.js 16 + Fumadocs (`fumadocs-core`, `fumadocs-ui`, `fumadocs-mdx`), with `fumadocs-openapi` generating the API reference and `lucide-react` for page icons.

The API is documented at `docs.ordre.app/api-docs`, inside the same Fumadocs app that serves the internal guides. The OpenAPI spec is generated at build time from route registrations in `apps/api`, not maintained manually.

**How it works:**

1. Each controller folder includes a `.openapi.ts` file that registers the feature's request and response shapes against the same `@ordre/core/schemas` Zod schemas used by the controller
2. The `@asteasolutions/zod-to-openapi` library converts those Zod schemas into OpenAPI 3.x definitions - no schema duplication
3. The top-level `openapi.ts` entry point combines all `.openapi.ts` files and generates a single `openapi.json` spec
4. `fumadocs-openapi` turns that spec into MDX pages (one per operation) rendered with the Fumadocs UI, including an interactive request playground

**App structure:**

```
apps/docs/
├── public/
│   └── openapi.json          # Generated at build time from apps/api
├── content/
│   ├── docs/                 # Internal guides (/internal-docs)
│   └── api-docs/             # Generated from openapi.json (/api-docs)
├── src/                      # Next.js + Fumadocs app
└── package.json
```

**Hosting:** Deployed to `docs.ordre.app` via Vercel, protected by Vercel's built-in password protection during development and beta.

**Alternatives considered:** Scalar (polished standalone UI, but a separate look from the guides), Swagger UI (dated look and feel), Redoc (read-only, no API client).

## 🗂️ Three-Folder Convention

Each folder inside `src/` has a single, non-overlapping responsibility.

| Folder    | Responsibility                                                                                                                                                                                            |
| --------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `app/`    | Route definitions, layouts, and framework-level concerns (middleware, entry files, API routes). Re-exports views. No business logic. All apps use `app/` - the Board app nests routes under `app/pages/`. |
| `views/`  | Page UI components, page-level logic, tests, and Storybook stories.                                                                                                                                       |
| `shared/` | Cross-cutting code reused across multiple views: hooks, utils, types, i18n.                                                                                                                               |

**Flow example (Board app):**

```tsx
// 1. Route module - src/app/pages/home/home.tsx
import { HomePage } from '@/views/Home';
export default function Home() { return <HomePage />; }

// 2. View - src/views/Home/ui/HomePage.tsx
import { Button } from '@ordre/ui';

export function HomePage() { ... }

// 3. Test - src/views/BoardView/ui/BoardView.test.tsx
test('renders board timeline', () => { ... });
```

## 🌍 i18n Structure

**Initial languages:** English (`en`) and Portuguese (`pt`).

**Shared strings** (app constants, status labels, errors, common UI copy) live in `@ordre/i18n` and are merged with app-specific strings at runtime.

**Libraries per app:**

| App       | Library                                       | Locale detection                                               | URL prefix                                     |
| --------- | --------------------------------------------- | -------------------------------------------------------------- | ---------------------------------------------- |
| Marketing | `next-intl`                                   | Path-based via `next-intl` routing                             | `as-needed` - `en` no prefix, `pt` → `/br`     |

| Board     | `i18next` + `react-i18next` + `remix-i18next` | Order: custom path (`/br` → `pt`) → `lng` cookie → header      | `en` no prefix, `pt` → `/br` (via app helpers) |
