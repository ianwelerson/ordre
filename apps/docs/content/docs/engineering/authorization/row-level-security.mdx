Row-Level Security (RLS) is the **database half** of Ordre's [two-layer authorization](/internal-docs/engineering/authorization) - the backstop beneath RBAC. Even if a controller forgets a `WHERE workspace_id = ?`, Postgres refuses to return another tenant's rows. This page is the design/implementation reference; for the one-time role creation each database needs, see [Setup - Database Roles & RLS](/internal-docs/setup/database-roles).

## The two roles at runtime

The guarantee rests on the API connecting as a **restricted role**:

- **`ordre_app`** (via `DATABASE_URL`) - the runtime role. Not superuser, not `BYPASSRLS`. That last flag is the whole game: it's what makes policies actually apply.
- **owner** (`neondb_owner` / local superuser, via `DATABASE_OWNER_URL`) - runs migrations only. Owns the tables and bypasses RLS by design.

Creating these is the one manual step - see [Setup - Database Roles & RLS](/internal-docs/setup/database-roles).

## How a request carries its identity

Policies decide by reading a per-request Postgres setting, `app.user_id`. Getting that value onto the exact connection running the query is the core of the implementation.

```
authenticate → rlsContext → requireWorkspaceAccess → requireWorkspacePermission → controller
   sets req.user   opens the             (all downstream queries run through getDb())
                   RLS context
```

Two files do the work:

- [`config/db-context.ts`](https://github.com/ianwelerson/ordre/blob/main/apps/api/src/config/db-context.ts) - `runWithUser(userId, fn)` opens a transaction, pins `app.user_id` with `SET LOCAL`, and exposes that transaction through `getDb()`. Every request-path query uses `getDb()` instead of the global `db`.
- [`middlewares/rls-context.ts`](https://github.com/ianwelerson/ordre/blob/main/apps/api/src/adapters/express/middlewares/rls-context.ts) - mounted right after `authenticate`, wraps the rest of the request in `runWithUser`.

### Why a transaction, and why `SET LOCAL`

`SET LOCAL` sets a Postgres setting that is **scoped to the current transaction** and automatically wiped at commit/rollback. That auto-cleanup is the safety mechanism:

- The API uses a **connection pool** - physical connections are reused across requests. A session-level `SET` would persist on the connection after the request ended, and the next request to borrow it would inherit the previous user's identity. `SET LOCAL` cannot outlive its transaction, so it can't leak.
- **Neon's pooler is PgBouncer in transaction mode**, where a session `SET` isn't reliably pinned to a backend anyway. `SET LOCAL` inside a transaction is the only approach that works there.

So each authenticated request runs inside one transaction that carries `app.user_id`. A public/unauthenticated request gets no context - `app.user_id` is unset and policies match nobody (fail-closed).

<Callout>
  Because the transaction spans the request, keep requests **DB-only** - never
  `await` a slow third-party call (email, SMS) while it is open, or you pin a pooled
  connection for the duration. That is what the outbox pattern is for.
</Callout>

## The policies

Defined in [`0002_enable_rls.sql`](https://github.com/ianwelerson/ordre/blob/main/packages/db/src/migrations/0002_enable_rls.sql), applied automatically on `pnpm db:migrate` (as the owner).

**Helper functions:**

- `app_current_user_id()` - reads the `app.user_id` GUC, returns `NULL` when unset.
- `app_is_member(ws)` - is the caller a member of workspace `ws`? Declared `SECURITY DEFINER` so it runs with the owner's privileges and **bypasses RLS internally**. Without that, a policy on `workspace_member` that calls this function would recurse into itself forever. Hardened with `SET search_path = public, pg_temp` so it can't be tricked into reading an attacker-planted table.
- `app_workspace_has_members(ws)`, `app_can_access_member(member)`, `app_slug_exists(slug)` - narrower `SECURITY DEFINER` helpers for the bootstrap, the join table, and the public slug check.

**Coverage:** `ENABLE` + `FORCE ROW LEVEL SECURITY` on the five tenant tables (`workspace`, `workspace_member`, `workspace_location`, `workspace_invite`, `workspace_member_location`). The Better Auth tables (`user`, `session`, `account`, `verification`) are **deliberately excluded** - Better Auth reads them before we know who the caller is, so RLS there would block login.

Most policies gate on `app_is_member(workspace_id)`: you may see and change only rows in workspaces you belong to. `USING` controls which rows are visible/targetable; `WITH CHECK` controls which rows you may write.

## The create bootstrap

A brand-new workspace has no members yet, so the create transaction inserts in a specific order:

```
workspace  →  workspace_member (owner)  →  workspace_location  →  workspace_member_location
```

The **owner membership must be inserted second**. A transaction sees its own uncommitted writes, so once that row exists `app_is_member()` returns `true` for the rest of the transaction, and every later insert passes its policy. The `member_insert_bootstrap` policy allows exactly this: insert yourself as `owner`, only into a workspace that has no members yet.

## Gotchas (learned turning it on)

Enabling RLS broke six tests, and each failure was a real design flaw it caught before production:

<Callout type="warn">
  **`INSERT ... RETURNING` also applies the `SELECT` policy.** Drizzle's
  `.returning()` reads the row back, and during create you are not a member yet, so
  the read-back is denied. Fix: generate the id with `randomUUID()` up front and
  drop `.returning()` on the workspace insert.
</Callout>

<Callout type="warn">
  **A statement cannot see its own inserted row.** So `app_is_member()` is still
  false while the first membership row is being inserted - making your very first
  membership unreadable. Fix: `member_select` also allows
  `user_id = app_current_user_id()`, so you can always see your **own** membership rows.
</Callout>

<Callout type="warn">
  **RLS silently breaks unauthenticated reads.** The public slug-availability check
  has no `app.user_id`, so RLS hid every workspace and it always reported
  "available". Fix: `app_slug_exists()`, a `SECURITY DEFINER` helper that discloses
  a boolean, never a row.
</Callout>

## Error handling

`rlsContext` commits the request transaction when the response finishes, with one exception: a **5xx rolls back** (via an internal `RollbackSignal`), so a handler that errors after a partial write doesn't leave it committed. A 4xx commits - validation failures write nothing anyway.

## Testing

Tests run against the **same restricted role as production**. The split lives in [`test/owner-db.ts`](https://github.com/ianwelerson/ordre/blob/main/apps/api/src/test/owner-db.ts):

- **Migrations, `TRUNCATE`, and seeding run as the owner** - they're owner operations `ordre_app` can't do.
- **The app under test connects as `ordre_app`**, so every integration test exercises the real RLS-enforced role.

## Operational notes

- **Effective concurrency = pool size.** Each in-flight request holds one pooled connection for its transaction's lifetime. Longer hold times shrink throughput - another reason to keep requests DB-only.
- **Policies are evaluated per row.** `app_is_member` is an indexed `EXISTS` on the `(user_id, workspace_id)` unique index - sub-millisecond for single-row reads, but a reason to keep list reads scoped and paginated.
- **Background workers have no `app.user_id`.** A worker connecting as `ordre_app` would see zero rows under RLS. Workers that must read tenant data need their own connection strategy (see the outbox notes).
