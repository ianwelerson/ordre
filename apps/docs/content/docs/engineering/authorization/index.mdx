Ordre authorizes every request through **two independent layers**. They answer different questions, live in different places, and fail independently - which is the point.

| Layer                                     | Question                    | Where it lives                          | Enforced by                                                       |
| ----------------------------------------- | --------------------------- | --------------------------------------- | ----------------------------------------------------------------- |
| **[RBAC](/internal-docs/engineering/authorization/rbac)** | _What actions_ can a role take? | Express middleware (app)                | `requireWorkspaceAccess` / `requireWorkspacePermission`, `can()`  |
| **[RLS](/internal-docs/engineering/authorization/row-level-security)** | _Which rows_ can it touch at all? | Postgres policies (database)            | Row-Level Security on every tenant table                          |

**RBAC is the primary gate; RLS is the backstop.** RBAC decides whether the action is allowed and returns clean `403`/`404` responses. RLS is the safety net underneath: even if a controller forgets a `WHERE workspace_id = ?`, or a permission check is wired wrong, the database physically refuses to return another tenant's rows. You have to defeat both to leak data.

## The request pipeline

For an authenticated workspace route, middleware runs in this order:

```
authenticate → rlsContext → requireWorkspaceAccess → requireWorkspacePermission → controller
```

| Stage                        | Responsibility                                              | Failure |
| ---------------------------- | ---------------------------------------------------------- | ------- |
| `authenticate`               | Resolve the session, set `req.user`                        | `401 UNAUTHORIZED` |
| `rlsContext`                 | Open the RLS transaction, pin `app.user_id` (RLS layer)    | -       |
| `requireWorkspaceAccess`     | Resolve the workspace, load the caller's **active** membership, set `req.member` | `404 NOT_FOUND` / `403 MEMBER_ACCESS_SUSPENDED` |
| `requireWorkspacePermission` | Check the role holds the required permission               | `403 FORBIDDEN` |
| controller                   | Do the work; shape the payload by role (`scopeRelations`)  | -       |

So the two layers interleave: `rlsContext` (RLS) sets identity before the RBAC guards run, so the guards' own membership lookup already runs under RLS too.

## Why both, not one

- **RBAC alone** gives good UX (precise `403`s, permission-driven UI) but is only as safe as the code - one missing filter leaks data.
- **RLS alone** guarantees isolation but returns blunt "empty result" instead of a meaningful error, and can't express "admins may update, members may not."

Together: RBAC for expressive, action-level control; RLS for a guarantee that doesn't depend on remembering to filter. Read each layer's page for its implementation.
