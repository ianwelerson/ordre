RBAC is the **application half** of Ordre's authorization - it decides _what actions_ a workspace member may take. For how it sits alongside RLS, see [Authorization](/internal-docs/engineering/authorization). The whole model lives in [`packages/core/src/permissions`](https://github.com/ianwelerson/ordre/blob/main/packages/core/src/permissions/workspace.ts), so the same rules are shared between the API (enforcement) and the UI (`can()` for conditional rendering).

## Permissions, not roles

The core decision: code checks **permissions**, never role names. A permission is a `domain:resource:action` string, and the catalog is the source of truth:

```ts
export const WORKSPACE_PERMISSIONS = [
  'workspace:read', 'workspace:update', 'workspace:delete',
  'workspace:member:read', 'workspace:member:manage',
  'workspace:location:read', 'workspace:location:manage',
  'workspace:subscription:read', 'workspace:subscription:manage',
] as const;
```

Why permissions over `if (role === 'admin')`: adding a role or shifting what a role can do becomes a **data change in one table**, not scattered role checks across controllers. It also reads as intent - `can('workspace:delete')` says what's needed; `role === 'owner'` makes you guess why.

## The role map

Each role is granted a set of permissions (`WORKSPACE_ROLE_PERMISSIONS`):

| Permission                    | owner | admin | member |
| ----------------------------- | :---: | :---: | :----: |
| `workspace:read`              |   ✓   |   ✓   |   ✓    |
| `workspace:update`            |   ✓   |   ✓   |        |
| `workspace:delete`            |   ✓   |       |        |
| `workspace:member:read`       |   ✓   |   ✓   |   ✓    |
| `workspace:member:manage`     |   ✓   |   ✓   |        |
| `workspace:location:read`     |   ✓   |   ✓   |   ✓    |
| `workspace:location:manage`   |   ✓   |   ✓   |        |
| `workspace:subscription:read` |   ✓   |   ✓   |   ✓    |
| `workspace:subscription:manage` |  ✓  |       |        |

One function does every check:

```ts
can(role, permission); // e.g. can('admin', 'workspace:delete') -> false
```

## Enforcement: two guards

Two middlewares split the work; both run after `authenticate` and `rlsContext` (see the [pipeline](/internal-docs/engineering/authorization)).

**`requireWorkspaceAccess`** - resource-level. Resolves the workspace from `:id` or `:slug`, loads the caller's `workspace_member` row, requires it to be `active`, and sets `req.member` (`{ id, workspaceId, role }`).

<Callout type="warn">
  It returns **`404 NOT_FOUND` both when the workspace doesn't exist and when the
  caller isn't a member** - deliberately indistinguishable, so membership can't be
  used to probe which workspaces exist. A non-member never learns the difference
  between "no such workspace" and "not yours".
</Callout>

A **suspended** member is the exception to that masking: they get `403 MEMBER_ACCESS_SUSPENDED` instead of a `404`. They already know the workspace exists - they used to be in it - so hiding it would leak nothing and would only obscure why they're locked out. Because the check sits in the access guard, it holds for every workspace route including the self-service ones (`/me`, `/leave`) that need no permission at all.

**`requireWorkspacePermission(permission)`** - action-level. Reads `req.member.role` and tests it with `can()`; a role lacking the permission gets `403 FORBIDDEN`. If `req.member` is missing it **throws (500)** rather than returning 403 - a missing member means the route forgot to mount `requireWorkspaceAccess` first, and masking a wiring bug as a permission error would hide it.

Wiring a route is then declarative:

```ts
workspaceRouter.delete(
  workspaceItemByIdPath,
  requireWorkspaceAccess,
  requireWorkspacePermission('workspace:delete'),
  sendMemberResult((req) => workspaceDelete(req.params.id))
);
```

## Relation-level shaping

Route guards are all-or-nothing per endpoint. But a single workspace read returns different **relations** depending on role - a member shouldn't receive the invite list, an admin should. `scopeRelations` handles that _before the query runs_:

```ts
// WORKSPACE_RELATION_PERMISSIONS maps each relation to the permission it needs
scopeRelations('member', { members: true, invites: true }); // -> { members: true }
```

It drops any relation the role can't see, so the unauthorized data is **never even fetched** (default-deny: a relation not in the map is dropped). The API contract stays role-agnostic - relations are optional in the `Workspace` type - while the payload is role-dependent at runtime.

## Response semantics

| Situation                          | Status | Returned by                  |
| ---------------------------------- | ------ | ---------------------------- |
| No session                         | `401`  | `authenticate`               |
| Not a member (or workspace absent) | `404`  | `requireWorkspaceAccess`     |
| Suspended member                   | `403`  | `requireWorkspaceAccess`     |
| Member, but lacks the permission   | `403`  | `requireWorkspacePermission` |

The `404`-not-`403` for non-members is the one deliberate choice worth remembering: **hide existence from outsiders, report permission honestly to insiders.** A suspended member counts as an insider.

## Extending it

New resources follow the same shape. When boards arrive, add `board:*` permissions to the catalog, grant them in the role map, and gate routes with `requireWorkspacePermission('board:...')` - no new mechanism, just more data.
