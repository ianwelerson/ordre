This is the field-level map of the Ordre database, derived from every product
screen (registration, dashboard, boards, the public client board, and settings).
It exists so tables can be created by hand with a complete picture of what each
screen needs.

Most of it is therefore a **specification, not a description**. Twelve tables
exist today; everything else on this page is a design waiting to be built.

Two modelling decisions are baked in:

- **Custom tables for workspace / member / invitation** - Ordre does not use the
  Better Auth organization plugin. Those are first-class tables here. Better Auth
  still owns `user`, `session`, `account`, and `verification`.
- **One table per activity-feed type** - the board feed is not a single
  polymorphic table. Each event kind (update, approval, milestone, internal note,
  visit report, stage transition, system event) is its own table.

## 📊 What exists today

[`packages/db/src/schemas/`](https://github.com/ianwelerson/ordre/tree/main/packages/db/src/schemas)
is the only source of truth for what the database holds. Every section below is
marked against it:

| Marker        | Meaning                                                                                                                           |
| ------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| ✅ **Built**   | The table is in the schema and has a migration. The fields, enums, and indexes listed match it.                                   |
| 📋 **Planned** | Designed here, not created yet. Names, types, and enums are proposals, and get checked against reality when the table is written. |

The twelve built tables, by schema file:

| Schema file                  | Tables                                                                                                 |
| ---------------------------- | ------------------------------------------------------------------------------------------------------ |
| `better-auth.ts` (generated) | `user`, `session`, `account`, `verification`                                                           |
| `workspace.ts`               | `workspace`, `workspace_location`, `workspace_member`, `workspace_member_location`, `workspace_invite` |
| `billing.ts`                 | `plan`, `workspace_subscription`                                                                       |

Everything else - clients, templates, boards, the activity feed, media,
messaging, channels, user preferences, and add-ons - is planned. The product
surfaces that would read those tables are not built either, so nothing is
blocked on them; see [Launch Scope](/internal-docs/product/roadmap/launch) for
the order they arrive in.

<Callout type="warn">
  A planned section is a proposal, not a promise. Do not write code against a
  table marked 📋, and when one is finally created, update its section here in
  the same change so the marker flips with the migration.
</Callout>

### Notation

Table and column names below are the real Postgres ones: snake_case tables,
camelCase Drizzle fields over snake_case columns.

> `timestamp` below always means Postgres `timestamptz` (timestamp **with** time
> zone) - every instant in Ordre is stored zone-aware.
>
> `[derived]` marks values computed at read time - do not store them.
> `[sensitive]` marks fields blurred on the client board until identity is verified
> (see [Board Access & Identity Verification](/internal-docs/product/specs)).

## 🔐 Better Auth Tables

✅ **Built** - `packages/db/src/schemas/better-auth.ts`

> **Managed by Better Auth.** These four tables (`user`, `session`, `account`,
> `verification`) are generated and owned by Better Auth - do not hand-edit their
> schema. The structure below mirrors the generated definition; profile and
> registration extras that used to live here now sit on the **`member`** table.

`packages/db/src/schemas/better-auth.ts` is emitted by the Better Auth CLI, so the
next `pnpm --filter api auth:generate` overwrites anything written there by hand.

That generator has no options for two fixes the timestamp columns need, so
`auth:generate` chains `auth:patch` (`packages/db/scripts/patch-better-auth-schema.ts`),
which rewrites its output: timestamps become timezone-aware, and `updated_at` gets
a default, since the generator marks it `NOT NULL` without one and inserts that do
not set it explicitly fail. The rules are idempotent and keyed off shapes rather
than table names, and the script **fails the command** when it cannot apply one,
because a silent no-op would mean losing time zones without noticing.

Everything Better Auth addresses by name (tables, columns, schema properties) is
left exactly as generated, so its adapter and tooling see the standard schema.
Cosmetic differences such as index naming and import order are deliberately not
patched: they buy nothing and add divergence to maintain.

## 👥 Member

✅ **Built** - `packages/db/src/schemas/workspace.ts`

A user's membership in a workspace (`workspace_member`). Custom table - not the
Better Auth org plugin.

`locale` sits here rather than on `user` so one person can read one workspace in
English and another in Portuguese. It is seeded from the request's
`Accept-Language` when the membership is created - on workspace creation, and
inside `app_invite_accept` on a first-time join - and the invite email is rendered
in the *inviter's* locale, since its recipient has no membership yet. See
[Transactional Outbox](/internal-docs/engineering/outbox#copy-and-locale).

| Field         | Type                            | Notes                                                    |
| ------------- | ------------------------------- | -------------------------------------------------------- |
| `id`          | uuid                            |                                                          |
| `userId`      | fk → user                       | `on delete cascade`                                      |
| `workspaceId` | fk → workspace                  | `on delete cascade`                                      |
| `displayName` | text, nullable                  | Name shown to clients on boards (first name works well)  |
| `title`       | text, nullable                  | Role label under the name on the client board            |
| `role`        | enum `owner \| admin \| member` |                                                          |
| `status`      | enum `active \| suspended`      | Suspended = soft-removed; the row is kept, access is not |
| `phone`       | text, nullable                  | Personal account contact (Register step 4, Profile)      |
| `locale`      | enum `en \| pt`, default `en`    | The language this member reads the product and its email in |
| `createdAt`   | timestamp                       |                                                          |
| `updatedAt`   | timestamp                       |                                                          |

Unique: (`userId`, `workspaceId`), as `workspace_member_user_workspace_unique`.
Index: `workspace_member_workspace_id_idx` on (`workspaceId`); `userId` lookups
are served by the leftmost column of the unique.

There is no `invited` status - an invitation lives in `workspace_invite`
until it is accepted, and only then does a member row exist. Removing a member
(or a member leaving) **soft-removes**: `status` becomes `suspended`, `role` resets
to `member` and `phone` is cleared, while `displayName` and `title` are kept for
audit and for reactivation on re-invite. `requireWorkspaceAccess` rejects a
suspended member with `403 MEMBER_SELF_SUSPENDED` before any permission check
runs, but the row stays visible in the member list - an admin has to see it to
lift the suspension.

`[derived]`: open-board count, last active (from sessions).

## ✉️ Invitation

✅ **Built** - `packages/db/src/schemas/workspace.ts`

Pending teammate invites (`workspace_invite`; Team → Invite modal).

| Field               | Type                                                         | Notes                                                       |
| ------------------- | ------------------------------------------------------------ | ----------------------------------------------------------- |
| `id`                | uuid                                                         |                                                             |
| `email`             | text                                                         |                                                             |
| `name`              | text                                                         | Name of the person being invited - used in the invite email |
| `role`              | enum `owner \| admin \| member`                              | Shares `workspace_member_role`                              |
| `workspaceId`       | fk → workspace                                               | `on delete cascade`                                         |
| `locationId`        | fk → workspace_location, nullable                            | Location they're invited to                                 |
| `invitedByMemberId` | fk → workspace_member, nullable                              | `on delete set null` - null for system/seed invites         |
| `token`             | text                                                         | Invite-link token                                           |
| `status`            | enum `pending \| accepted \| declined \| expired \| revoked` |                                                             |
| `expiresAt`         | timestamp                                                    |                                                             |
| `createdAt`         | timestamp                                                    |                                                             |
| `updatedAt`         | timestamp                                                    |                                                             |

**Partial** unique on (`workspaceId`, `email`) **where `status = 'pending'`**, as
`workspace_invite_workspace_email_pending_unique`. Only one invite per address can
be outstanding at a time, while expired, declined, and revoked rows accumulate and
never block a re-invite.

The partial unique is filtered, so it cannot serve the foreign keys. Those are
indexed explicitly: `workspace_invite_workspace_id_idx`,
`workspace_invite_location_id_idx`, and
`workspace_invite_invited_by_member_id_idx`. A fourth,
`workspace_invite_pending_expiry_idx` on (`expiresAt`) where `status = 'pending'`,
backs the sweep for invites that have run out.

## 📍 Location

✅ **Built** - `packages/db/src/schemas/workspace.ts`

A physical site (`workspace_location`). Every workspace has at least one; every
board belongs to one.

| Field         | Type                   | Notes                  |
| ------------- | ---------------------- | ---------------------- |
| `id`          | uuid                   |                        |
| `workspaceId` | fk → workspace         | `on delete cascade`    |
| `name`        | text                   | "Geneva · Grand-Rue"   |
| `address`     | text, nullable         |                        |
| `latitude`    | numeric(8,6), nullable | For map pin            |
| `longitude`   | numeric(9,6), nullable | For map pin            |
| `phone`       | text, nullable         | Board "Workshop phone" |
| `email`       | text, nullable         |                        |
| `isDefault`   | boolean                | Default false          |
| `createdAt`   | timestamp              |                        |
| `updatedAt`   | timestamp              |                        |

**Partial** unique on (`workspaceId`) **where `isDefault`**, as
`workspace_location_one_default_per_workspace` - at most one default location per
workspace, with the other rows unconstrained. Index:
`workspace_location_workspace_id_idx` on (`workspaceId`).

`latitude` and `longitude` are `numeric`, Postgres' exact decimal type, so a
coordinate survives a round trip unchanged. Scale 6 resolves to about 11cm.
Proximity search ("locations within 5km") would need PostGIS
`geography(Point, 4326)`; independent numerics cannot index distance.

## 💳 Billing

### `plan`

✅ **Built** - `packages/db/src/schemas/billing.ts`

The plan catalog - the subscribable tiers and their limits. Global, not
workspace-scoped. Seeded from [`packages/db/src/seeds/plan.ts`](https://github.com/ianwelerson/ordre/blob/main/packages/db/src/seeds/plan.ts);
there is no admin API for plans.

| Field          | Type                              | Notes                                                                        |
| -------------- | --------------------------------- | ---------------------------------------------------------------------------- |
| `id`           | uuid                              |                                                                              |
| `code`         | enum, unique                      | `<tier>:<variant>`, e.g. `free:founding`                                     |
| `tier`         | enum `free \| paid`               | Derived from `code`, stored so it can back the index                         |
| `status`       | enum `active \| legacy \| closed` |                                                                              |
| `title`        | text                              | Display name                                                                 |
| `description`  | text                              |                                                                              |
| `entitlements` | jsonb                             | `{ limits: { seat?, location? } }` - defaults to `{ limits: {} }`, see below |
| `createdAt`    | timestamp                         |                                                                              |
| `updatedAt`    | timestamp                         |                                                                              |

Unique: (`code`); partial unique on (`tier`) where `status = 'active'`, as
`plan_one_active_per_tier`, so "the current free/paid plan" is a single
well-defined row while legacy plans of the same tier coexist. `tier` is derivable
from `code` but stored anyway, because an index expression over `code::text` is
not allowed - the enum cast is not `IMMUTABLE`.

**Limits live in `entitlements`, not in columns.** A new limit is a new key in the
`PLAN_LIMITS` enum with no migration. Within `limits`, a number caps the resource,
and `null` - or the key being absent - means unlimited:

```jsonc
{ "limits": { "seat": 2, "location": 1 } } // free:founding
{ "limits": { "seat": 20, "location": 3 } } // paid:founding
```

A **seat** is held by an active member *or* a pending invite, the workspace owner
included - so it counts people the workspace has committed to, not members it
currently has. `requireWorkspaceQuota` enforces both limits at the routes that
consume one (see [Authorization](/internal-docs/engineering/authorization)).

Because the blob is JSONB, Postgres will accept a typo'd key that the type system
never sees, and an unrecognised key would read as "unlimited". The guard therefore
re-validates `entitlements` against its Zod schema on every check and refuses the
request (`500 PLAN_ENTITLEMENTS_INVALID`) rather than treating a malformed plan as
uncapped.

## 📤 Outbox

✅ **Built** - `packages/db/src/schemas/outbox.ts`

`outbox` - one row per **delivery**, written in the same transaction as the
business data that produced it. The delivery worker claims rows and sends them
after that transaction commits. See [Transactional Outbox](/internal-docs/engineering/outbox)
for the claim protocol, retry schedule, and how to add a topic.

| Field           | Type                | Notes                                                                                                                                         |
| --------------- | ------------------- | --------------------------------------------------------------------------------------------------------------------------------------------- |
| `id`            | uuid                | Also the provider's idempotency key - never reuse or regenerate it                                                                            |
| `channel`       | enum `email`        | Routes the row to a provider. Postgres enum - a new value is a migration                                                                      |
| `topic`         | enum                | The business event: `account:created`, `account:verify-email`, `account:reset-password`, `workspace:created`, `invite:created`. Postgres enum |
| `payload`       | jsonb               | `{ to, variables }` only. The template is resolved from `channel:topic` at send time, never stored                                            |
| `attempts`      | int                 | Incremented at **claim** time, so a crash mid-send still counts                                                                               |
| `nextAttemptAt` | timestamp           | When the row becomes claimable again; backoff is written here                                                                                 |
| `claimedAt`     | timestamp, nullable | Set on claim; a row stuck here >5 min is re-claimed as orphaned                                                                               |
| `processedAt`   | timestamp, nullable | Non-null = delivered. The only terminal success state                                                                                         |
| `lastError`     | text, nullable      | Flattened error from the last failed attempt                                                                                                  |
| `createdAt`     | timestamp           | Also the age cap - rows older than 23h stop being claimed                                                                                     |
| `updatedAt`     | timestamp           |                                                                                                                                               |

Partial index `outbox_pending_idx` on (`nextAttemptAt`) **where `processedAt IS NULL`**,
so claims stay cheap no matter how many delivered rows have accumulated.

<Callout type="warn">
  **Deliberately not under RLS.** The worker connects as `ordre_app` with no
  `app.user_id` set, so any policy would evaluate against a NULL user, return zero
  rows, and the queue would look permanently empty while silently sending nothing.
  The table holds no tenant rows to leak - only a recipient address and the
  variables for one message.
</Callout>

There is no `status` column. State is derived: unprocessed and due, unprocessed and
waiting, delivered (`processedAt` set), or dead-lettered (attempts exhausted or past
the age cap, so the claim filter can never pick it up again).
